# GPL-3.0-only firmware over ESP-IDF's binary radio libraries

Research date: 2026-09-15

ADR [0025](../adr/0025-use-osi-approved-strong-copyleft-licensing.md) already settled that project-authored software, including the firmware, is licensed `GPL-3.0-only`; that choice is not revisited here. This note instead checks a narrower, safety-critical question: ESP-IDF (the ESP32-WROOM-32E SDK) ships precompiled static libraries for the WiFi and Bluetooth radio stacks (`libnet80211.a`, `libpp.a`, `libphy.a`, `libcore.a`, `libbtdm_app.a`/`libbt.a`, and similar), and the firmware image statically links against them. Does GPLv3's "System Library" exception cleanly excuse those blobs from the GPL work's source-disclosure obligation, or does the firmware's design create a conflict GPL-3.0-only cannot satisfy? Statements under **Verified** are traced to the GPLv3 license text, Espressif's own license files in the `espressif` GitHub organization, Tasmota's own license/docs, a real historical GPL-compliance dispute against Espressif, and the FSF's GPL FAQ. Statements under **Recommendation** are this project's design judgment built on those facts.

## 1. What GPLv3 itself says about System Libraries

**Verified.** GPLv3 Section 0, "Definitions," defines the exception narrowly and ties it to a specific, limited kind of component:

> The "System Libraries" of an executable work include anything, other than the work as a whole, that (a) is included in the normal form of packaging a Major Component, but which is not part of that Major Component, and (b) serves only to enable use of the work with that Major Component, or to implement a Standard Interface for which an implementation is available to the public in source code form. A "Major Component", in this context, means a major essential component (kernel, window system, and so on) of the specific operating system (if any) on which the executable work runs, or a compiler used to produce the work, or an object code interpreter used to run it.

Section 1, "Source Code," then excludes System Libraries from "Corresponding Source," but immediately narrows that exclusion with a counter-example that describes exactly the static-linking pattern firmware uses:

> The "Corresponding Source" for a work in object code form means all the source code needed to generate, install, and (for an executable work) run the object code and to modify the work, including scripts to control those activities. However, it does not include the work's System Libraries, or general-purpose tools or generally available free programs which are used unmodified in performing those activities but which are not part of the work. For example, Corresponding Source includes interface definition files associated with source files for the work, and the source code for shared libraries and dynamically linked subprograms that the work is specifically designed to require, such as by intimate data communication or control flow between those subprograms and other parts of the work.

Section 6, "Conveying Non-Source Forms," separately confirms the exception's practical effect on the binary itself, not only on source-disclosure duties: "A separable portion of the object code, whose source code is excluded from the Corresponding Source as a System Library, need not be included in conveying the object code work." [GPLv3 full text, gnu.org](https://www.gnu.org/licenses/gpl-3.0.html) (verified against the canonical text served at `https://www.gnu.org/licenses/gpl-3.0.txt`)

Two structural points matter for firmware specifically. First, "Major Component" is defined narrowly as the kernel/window-system/compiler/interpreter of "the specific operating system... on which the executable work runs" — not "any SDK component the vendor ships." Second, the System Library test has two independent prongs, both of which must hold: the component must be normally packaged with that Major Component but not part of it, **and** it must either merely enable use with that Major Component or implement a public, source-available Standard Interface. The WiFi/BT proprietary MAC and PHY protocols are not "Standard Interfaces... available to the public in source code form" in the GPLv3 sense, so only the first branch of prong (b) is available, and Section 1's own example — "shared libraries and dynamically linked subprograms that the work is specifically designed to require, such as by intimate data communication or control flow" — describes statically-linked, tightly-coupled embedded radio-stack libraries far better than it describes a generic system library like libc.

**Recommendation.** Treat the "System Library" exception as a real but genuinely contestable defense for these specific components, not a settled safe harbor. Do not structure the licensing story around "these blobs are System Libraries, so we have no obligation" as the sole basis for shipping GPL-3.0-only firmware — the license text itself supplies a strong counter-reading (intimate, specifically-required, statically-linked subprograms are Corresponding Source), and Section 4 below shows this exact fact pattern has already produced a real dispute with Espressif that Espressif did not resolve by successfully asserting the exception.

## 2. What Espressif's own license files actually say

**Verified.** For the ESP32 classic target (ESP32-WROOM-32E), ESP-IDF's WiFi, Bluetooth-controller, and PHY binary libraries are not stored directly in the `espressif/esp-idf` tree — they are git submodules pointing at separate binary-only repositories:

- `components/esp_wifi/lib` → [`espressif/esp32-wifi-lib`](https://github.com/espressif/esp32-wifi-lib) (contains `libnet80211.a`, `libpp.a`, `libcore.a`, and related WiFi stack binaries)
- `components/bt/controller/lib_esp32` → [`espressif/esp32-bt-lib`](https://github.com/espressif/esp32-bt-lib) (contains `libbtdm_app.a` and the classic-ESP32 Bluetooth controller binary)
- `components/esp_phy/lib` → [`espressif/esp-phy-lib`](https://github.com/espressif/esp-phy-lib) (contains `libphy.a`)

Each of these repositories ships its own `LICENSE` file, and all three are the plain **Apache License, Version 2.0** text — not a bespoke "Espressif Binary Library License." [`esp32-wifi-lib/LICENSE`](https://github.com/espressif/esp32-wifi-lib/blob/master/LICENSE), [`esp32-bt-lib/LICENSE`](https://github.com/espressif/esp32-bt-lib/blob/master/LICENSE), [`esp-phy-lib/LICENSE`](https://github.com/espressif/esp-phy-lib/blob/master/LICENSE)

`esp32-wifi-lib`'s `README.rst` states this explicitly and flags that only the compiled ("Object") form is provided:

> These binary libraries are provided under the same license as the parent esp-idf project - the Apache License 2.0 as provided in the file LICENSE. (The license text refers to this as "Object" form.)

[`esp32-wifi-lib/README.rst`](https://github.com/espressif/esp32-wifi-lib/blob/master/README.rst)

The parent `espressif/esp-idf` repository is itself Apache-2.0 ([`esp-idf/LICENSE`](https://github.com/espressif/esp-idf/blob/master/LICENSE)), and Espressif's own "Copyrights and Licenses" documentation page confirms "All original source code in this repository is Copyright (C) 2015-2023 Espressif Systems. This source code is licensed under the Apache License 2.0," while cataloguing the various third-party-licensed pieces bundled into the firmware image (Newlib/BSD, FreeRTOS/MIT, LWIP/BSD, wpa_supplicant/BSD, Mbed TLS/Apache-2.0, and others) — none of which is listed as GPL-incompatible. [ESP-IDF "Copyrights and Licenses"](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/COPYRIGHT.html)

Apache License 2.0 permits redistribution of unmodified Object-form works without also requiring the licensor to publish Source form — Apache-2.0 has no copyleft/source-disclosure obligation of its own, unlike GPL. So Espressif's terms *do* permit redistributing these `.a` files as part of a larger product; the license itself is not the obstacle. The FSF's license list separately confirms Apache License 2.0 is one-way compatible with GPLv3 (Apache-2.0 code may be included in a GPLv3-covered combined work; the reverse is not true, and Apache-2.0 is explicitly GPLv2-incompatible over its patent clauses). [GNU license list, "Apache License 2.0"](https://www.gnu.org/licenses/license-list.html#apache2)

**Recommendation.** Apache-2.0 licensing removes any concern about *redistributing* the `.a` files themselves — that permission is clearly and unambiguously granted, and it is compatible with combining into a GPLv3 work. The unresolved problem is narrower and purely about GPLv3's own **Corresponding Source** duty: Espressif never publishes source for `esp32-wifi-lib`, `esp32-bt-lib`, or `esp-phy-lib` (they are "Object" form only, by their own README's own words), so if these libraries are ultimately found to be "part of the work" rather than excluded System Libraries, GPL-3.0-only cannot be satisfied for them — not because Espressif forbids it, but because the source simply is not available to provide, from Espressif or anyone else. Record the exact upstream repository, commit/tag, and Apache-2.0 license text for each linked binary component in `THIRD_PARTY_NOTICES.md`, distinct from the freely-available-source components (FreeRTOS, LWIP, Mbed TLS, etc.).

## 3. Precedent: real GPL-firmware projects on the same category of blobs

**Verified.** Tasmota (`arendst/Tasmota`), a GPL-3.0-licensed firmware project running on both ESP8266 and ESP32 hardware, ships the unmodified, unedited canonical GPLv3 license text as `LICENSE.txt` — it contains no added Section 7 "additional permission" notice, no linking exception, and no carve-out language for the Espressif/Arduino SDK components it links against. [`Tasmota/LICENSE.txt`](https://github.com/arendst/Tasmota/blob/development/LICENSE.txt) Tasmota's `README.md` "License" section is a single unelaborated sentence: "This program is licensed under GPL-3.0-only," again with no discussion of the underlying vendor SDK. [`Tasmota/README.md`](https://github.com/arendst/Tasmota/blob/development/README.md) No FAQ, wiki page, or license addendum addressing this specific SDK-linking question was found in Tasmota's own repository or documentation site. Tasmota is therefore evidence that shipping GPL-3.0-only firmware over Espressif's binary radio stack is common, widely-tolerated practice — **not** evidence that the question has been formally or explicitly resolved; Tasmota simply does not address it in writing anywhere discoverable.

A materially closer precedent exists and is directly on point: in December 2014, a GPL compliance request was filed as [`espressif/ESP8266_RTOS_SDK` issue #1](https://github.com/espressif/ESP8266_RTOS_SDK/issues/1) against Espressif's own then-GPLv3-licensed `esp_iot_rtos_sdk`, naming exactly this category of components as undisclosed binary-only code lacking source: `lib/libmain.a`, `lib/libnet80211.a`, `lib/libphy.a`, `lib/libpp.a`, `lib/libwpa.a`. The ensuing discussion is a real-world airing of precisely the question this note investigates:

- The complainant (Paul Sokolovsky) argued the blobs are ad hoc application libraries "statically linked with GPL source code," not System Libraries, and that shipping a GPLv3 SDK this way leaves every downstream hardware vendor "in violation of GPL" because they cannot obtain source to pass on to their own customers.
- A commenter (bryanlyon) argued the opposite: that the blobs "clearly fall under 'System Libraries, or general-purpose tools'" and quoted GPLv3 Section 1's Corresponding Source definition in support.
- Espressif itself (user `espressif`, posting as "John Lee") responded: "we are sorry that we screwed up on GPL thing... we have decided we are not able to open source our MAC, and the low level drivers... To address this, we decide that perhaps it is better to move to GPLv2." Community members immediately pointed out GPLv2 has the same problem.
- Espressif's actual resolution, four months later, was not to assert or rely on the System Library exception at all: it re-released the entire `esp_iot_rtos_sdk` (SDK 1.1.0) under the **MIT License** instead of GPL, sidestepping the copyleft source-disclosure question entirely rather than defending the "System Library" characterization of the blobs.

[`espressif/ESP8266_RTOS_SDK` issue #1, full thread](https://github.com/espressif/ESP8266_RTOS_SDK/issues/1)

**Recommendation.** This is the single most important fact this research turned up: the entity that actually controls these binary libraries was confronted with this exact question for this exact category of component (WiFi MAC/PHY blobs under a GPL SDK license) and chose to abandon GPL for the surrounding code rather than stand behind the System Library defense. That is strong practical evidence the defense is not reliably safe to lean on alone. Tasmota's long, apparently incident-free track record shows the risk has not materialized as enforcement in practice — likely because no copyright holder in the *application* code (as opposed to Espressif's SDK, which is what triggered the 2014 dispute) has had standing or motive to press the point — but it is silence, not resolution, and should not be read as legal clearance.

## 4. FSF guidance on linking against non-free/system-provided libraries

**Verified.** The GNU GPL FAQ's `SystemLibraryException` entry confirms the exception exists precisely for this scenario (a GPL program needing a GPL-incompatible library that ships with its platform) but is conditioned strictly on meeting GPLv3's own definitional criteria — it is not a general "anything the SDK vendor provides" escape hatch:

> Both versions of the GPL have an exception to their copyleft, commonly called the system library exception. If the GPL-incompatible libraries you want to use meet the criteria for a system library, then you don't have to do anything special to use them; the requirement to distribute source code for the whole program does not include those libraries, even if you distribute a linked executable containing them. ... GPLv3 explicitly defines "System Libraries" in section 1, to exclude it from the definition of "Corresponding Source."

[GNU GPL FAQ, "Can I link a GPL program with a proprietary system library?"](https://www.gnu.org/licenses/gpl-faq.html#SystemLibraryException)

Critically, the FAQ's `GPLIncompatibleLibs` entry is the FSF's own prescribed remedy for exactly the situation where a project is not confident the exception applies (or knows it doesn't): grant an **explicit additional permission under GPLv3 Section 7** covering the named library by name, rather than relying on the System Library exception:

> If you want your program to link against a library not covered by the system library exception, you need to provide permission to do that. ... If you're using GPLv3, you can accomplish this goal by granting an additional permission under section 7.

The FAQ then supplies a ready-to-use notice template, to be added to the covered source files, of the form: "If you modify this Program, or any covered work, by linking or combining it with [name of library] (or a modified version of that library), containing parts covered by the terms of [name of library's license], the licensors of this Program grant you additional permission to convey the resulting work." [GNU GPL FAQ, "What legal issues come up if I use GPL-incompatible libraries with GPL software?"](https://www.gnu.org/licenses/gpl-faq.html#GPLIncompatibleLibs)

The FAQ's `FSWithNFLibs` entry separately confirms this is a known, accepted (if regretted) pattern for free software that must depend on a non-free/closed library to function on particular hardware, and asks projects to document the dependency as a drawback rather than hide it. [GNU GPL FAQ, "Can I write free software that uses nonfree libraries?"](https://www.gnu.org/licenses/gpl-faq.html#FSWithNFLibs) Separately, `GPLInProprietarySystem` describes the general boundary for combined works — components that "remain well separated" and "communicate at arms length" can stay under separate licenses (mere aggregation), while components "combined so that they become effectively two parts of one program" cannot. [GNU GPL FAQ, "I'd like to incorporate GPL-covered software in my proprietary system"](https://www.gnu.org/licenses/gpl-faq.html#GPLInProprietarySystem) Statically-linked firmware calling into the radio-stack blobs via tight, synchronous, in-process function calls does not fit the FAQ's "arms length" description; that description fits, for example, a Host-side companion app talking to the firmware over UART/BLE, not the firmware's own internal linking.

**Recommendation.** Follow the FSF's own prescribed path rather than betting on the System Library exception resolving in the project's favor: add an explicit GPLv3 Section 7 additional permission, naming the specific Espressif binary components (`esp32-wifi-lib`, `esp32-bt-lib`, `esp-phy-lib`, and the concrete `.a` files/ESP-IDF components they back) and their Apache-2.0 license, granting downstream recipients permission to convey the firmware image linked against them without providing Corresponding Source for those specific components. This does two things at once: it makes the firmware's own distribution terms internally consistent regardless of how the System Library question would ultimately be decided, and it prevents the project from ever putting a downstream builder/flasher of the firmware in the position Espressif's own SDK users were put in during the 2014 dispute — holding a GPL-licensed binary they have no legal way to comply with.

## Direct recommendation

GPL-3.0-only is **not unconditionally safe** to apply to the firmware image exactly as currently planned, if "as planned" means relying solely on GPLv3's System Library exception to excuse the ESP-IDF WiFi/Bluetooth/PHY binaries from Corresponding Source. That reliance is legally contestable: GPLv3's own text (the "intimate data communication or control flow" language in Section 1) describes statically-linked, tightly-coupled subprograms as included in Corresponding Source, not excluded, and the one real-world case where a copyright holder pressed this exact question against Espressif over this exact category of component ended with Espressif abandoning GPL for the SDK rather than defending the exception. Tasmota's years of uneventful operation under GPL-3.0-only over the same category of blobs shows the practical enforcement risk is low, not that the legal question is settled.

GPL-3.0-only **is safe and enforceable with a documented, precise condition**: add an explicit GPLv3 Section 7 additional permission to the firmware's license notice, naming the exact Apache-2.0-licensed Espressif binary components the firmware links against (WiFi: `esp32-wifi-lib`; Bluetooth: `esp32-bt-lib`; PHY: `esp-phy-lib`, plus their constituent `.a` files) and granting recipients permission to convey the firmware linked against them without those specific components' Corresponding Source. This converts an ambiguous "maybe it's a System Library" defense into an unambiguous, self-granted permission that does not depend on how a court would read Section 0's "Major Component"/"Standard Interface" test. Concretely, this project's licensing documents should be updated to reflect:

1. **ADR 0025**: add a short addendum noting that `GPL-3.0-only` for the firmware is paired with a named Section 7 additional permission for Espressif's Apache-2.0 binary radio libraries, and why (this research).
2. **`THIRD_PARTY_NOTICES.md`**: list `esp32-wifi-lib`, `esp32-bt-lib`, and `esp-phy-lib` (with the specific ESP-IDF/tag or commit pin used) as Apache-2.0, Object-form-only, no-source-available components covered by the additional permission — distinct from the many other ESP-IDF-bundled components whose source *is* available (FreeRTOS, LWIP, Mbed TLS, wpa_supplicant, etc.) and need no such exception.
3. **Source headers / `LICENSE`**: add the FSF's suggested Section 7 notice text (adapted with this project's actual library names) to the firmware source, per the GPL FAQ's `GPLIncompatibleLibs` template.

This is a documentation-and-licensing-notice fix, not a legal dead end — but it is also not something this research note can finalize on its own. Because a real compliance dispute has already occurred over this precise fact pattern (the 2014 Espressif SDK case) and reasonable, informed people in that dispute read GPLv3's "System Library"/"intimate data communication" language in opposite directions, the project should have the drafted Section 7 additional-permission notice reviewed by a lawyer with FOSS-licensing experience before it ships as the operative license, rather than treating this note's recommendation as a substitute for that review.

# F08 — Prove combined hardware feasibility and resource budgets

- **Kind:** Feasibility gate
- **Detail:** Executable
- **Status:** In progress — the DRAM/IRAM capacity blocker is resolved (static buffers moved to the runtime heap; the board has 4 MB flash, not 2 MB), so both the full NimBLE host and the controller-only path now link and run with headroom. Remaining work is M1a's combined-load measurements: packet loss, channel revisit, NVS write rate, serial traffic, and touch under radio load. See the [feasibility record](../../hardware/profiles/lcdwiki-esp32-32e-2.8/development/feasibility.md#capacity-blocker-resolved-two-measurement-errors) and [F08a](F08a.md)
- **Milestones:** M1a
- **Depends on:** [F06](F06.md), [F07](F07.md)
- **Board:** Exclusive E32R28T session

Read [dispatch and completion rules](README.md#dispatch-and-completion) before starting. Command names below are planned deliverables, not tools that already exist.

## Outcome

A measured integrated build demonstrates that radio observation, UI/touch, USB traffic, and flash activity can coexist within a defensible MVP resource budget.

## Ownership and inputs

Own the combined feasibility harness, bounded radio probes, instrumentation, and `hardware/profiles/lcdwiki-esp32-32e-2.8/development/feasibility.md`. [F08a](F08a.md) owns the representative UI capacity slice and its independent runtime budget evidence. Coordinate any driver changes with F05–F07 owners. Consume [M1a](../../IMPLEMENTATION_PLAN.md) and [performance budgets](../mvp-validation.md).

## Work

1. Exercise passive WiFi and BLE separately and with explicit switching while rendering, touching, receiving representative complete-snapshot traffic, and writing flash. Keep capture payloads transient.
2. Measure switching gaps, revisit timing, observable loss/uncertainty, touch latency, animation behavior, CPU load, peak/minimum free RAM, and image size across idle and busy conditions. Distinguish measurement limits from receiver guarantees.
3. Resolve the three physical SPI buses against available controllers; compare candidate touch arrangements under combined load.
4. Produce byte budgets for firmware, buffers, NVS, maximum Alert/Baseline records, journal reclamation, and Operational/Capacity-pressure reservations. State checkpoint/write/endurance assumptions and safe provisional counts.
5. Record pass/fail against the declared performance method and required headroom. Resolve failures or revise scope explicitly before passing; add missing evidence to the gate rather than moving it downstream silently.

The current radio/UI capacity block is recorded in the board [feasibility
record](../../hardware/profiles/lcdwiki-esp32-32e-2.8/development/feasibility.md).
Complete [F08a](F08a.md) to establish the bounded operational-UI budget before
choosing the capacity path and resuming the combined physical run.

## Acceptance

- Results identify hardware, dependency/build versions, radio load, instrument method, UART load, coverage limits, and exact test conditions.
- Requested radio windows are not automatically counted as verified receive time; loss and uncertain intervals remain visible.
- One-second complete snapshots have measured serial headroom under a documented size estimate, to be rechecked with C01/TB02's actual messages.
- Partition/RAM budgets justify the proposed retained counts; 32/128/512 remain adjustable, with confirmed assumptions handed to later tickets.
- The board remains recoverable after the test. Passing M1a is a prerequisite for every production protocol/domain tracer ticket.

## Verification and handoff

Run `./dev check all` and `./dev run hardware -- feasibility --port "$CYD_PORT"`. Record physical operator actions, measurement logs, budget table, pass/fail rationale, and integrated commit. Simulator output alone cannot close this ticket. When radio reference equipment or measurement evidence is missing, keep the gate open and name the missing measurement.

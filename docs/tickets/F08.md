# F08 — Prove combined hardware feasibility and resource budgets

- **Kind:** Feasibility gate
- **Detail:** Executable
- **Status:** Done — the DRAM/IRAM capacity blocker is resolved (static buffers moved to the runtime heap; the board has 4 MB flash, not 2 MB), so both the full NimBLE host and the controller-only path now link and run with headroom. CPU load, NVS write-rate, touch-under-radio-load, and WiFi channel-hop switching-gap evidence are now recorded (`DEV:CPU_STATUS`, `DEV:NVS_WRITE_TEST`, a physical operator session exercising the capacity slice and a full calibration flow with radio reception running throughout, and a bounded channel-hop probe with `DEV:CHANNEL_STATUS` — all zero drops, no crash, board recoverable, and a WiFi channel switch measured at under 1 ms with no visible BLE reception stall). The hop probe now covers the full US channel range (1-11, FCC Part 15), at a dwell aligned to two 802.11 beacon periods (100 TU = 102.4 ms each, matching Kismet's own channel-hopping floor), ~210 ms/11 channels (~2.3 s revisit), with a dedicated beacon-frame counter that found real beacon activity on channel 9 the earlier 3-channel (1/6/11) probe could never have seen. BLE's side of switching is also now covered: `BleScanToggleTask`/`DEV:BLE_TOGGLE_STATUS` measured LE Set Scan Enable disable/enable round trips at 466 μs-1.1 ms (disable) and 1.4-5.4 ms (enable, more expensive and asymmetric, cheaper after the first couple of calls), with zero advertising reports leaking through during any of 17 deliberate "scan off" windows — a real, clean stop, not queued reports trickling in late. This is a bounded feasibility probe, not the product's eventual Observation Window scheduler (ADR 0003) or Channel Plan (ADR 0026), and has not yet been run combined with touch/UI load or with WiFi and BLE actually alternating exclusively (both still run continuously here; only BLE's own on/off was toggled). A temporary non-US superset probe (channels 1-14, not committed) confirmed `esp_wifi_set_channel()` reaches channels 12-14 cleanly with no failures and no cost cliff versus 1-11, without an explicit `esp_wifi_set_country()` call — tested for passive receive-only monitoring (WiFi promiscuous mode, passive BLE scan; no transmission attempted on any channel) — see the [feasibility record](../../hardware/profiles/lcdwiki-esp32-32e-2.8/development/feasibility.md#non-us-channel-superset-does-passive-monitoring-reach-12-14). It did not establish RF receive performance on those channels, any transmit behavior (untested and out of scope — the Monitor Device never transmits), or the country-config/regulatory question a real ADR 0026 Channel Plan preset would need. One-second serial traffic headroom now has a first measurement ahead of C01: [snapshot-size-estimate.md](../../hardware/profiles/lcdwiki-esp32-32e-2.8/development/snapshot-size-estimate.md) costs host-metrics.md's full field list in CBOR against ADR 0011's envelope to get a documented ~1,019-byte representative snapshot size (superseding the prior arbitrary 1,024-byte placeholder), and `serial_snapshot_probe.py` plus a new `DEV:SERIAL_RX_TEST` dev-console command measured zero-loss reception on the idle board from the product's required 1 Hz/~1 KB/s cadence up to an unpaced ~9,342 B/s (~9x headroom, near the 115200-baud ceiling) — see the [feasibility record](../../hardware/profiles/lcdwiki-esp32-32e-2.8/development/feasibility.md#one-second-serial-traffic-a-pre-c01-size-estimate-and-live-throughput-probe). This is idle-board throughput through the throwaway dev-console recovery path only, not the combined radio/UI/flash load, not real CBOR encode/decode cost, and not TB02's eventual interrupt-driven UART driver. The partition/write/endurance budget also now has a first pass: [partition-write-budget.md](../../hardware/profiles/lcdwiki-esp32-32e-2.8/development/partition-write-budget.md) costs a provisional 128-byte Alert / 96-byte Transmitter Baseline record design at the 32/128/512 targets (~68 KiB working set, ~204 KiB with a conservative 2x reclamation headroom — ~9.7x inside `partitions.csv`'s already-reserved 1.94 MiB `state` partition), and a new `DEV:PARTITION_WRITE_TEST` command measured real `esp_partition_erase_range`/`esp_partition_write` cost on the board (2,850 μs/4,096 B sector erase, 701-861 μs/128 B record write, zero failures), grounding a bounded (decades-of-margin, two stated assumptions) endurance estimate — see the [feasibility record](../../hardware/profiles/lcdwiki-esp32-32e-2.8/development/feasibility.md#partition-record-and-endurance-budget). Getting that measurement required fixing a stale local `firmware/sdkconfig` that had silently reverted to ESP-IDF's built-in single-app partition table instead of `partitions.csv`. The serial-headroom check now also covers combined load: run again at the product's 1 Hz/1,019-byte cadence on the same controller-only-BLE plus passive-Wi-Fi build with WiFi channel-hop and BLE scan toggle running continuously throughout, it measured 60/60 frames, 61,200/61,200 bytes, zero sequence gaps, and zero `DEV:HCI_STATUS` command_failures/malformed_events/dropped_events before and after, with the board fully responsive and MicroSD still mounted afterward — see the [feasibility record](../../hardware/profiles/lcdwiki-esp32-32e-2.8/development/feasibility.md#combined-load-result-serial-traffic-alongside-continuous-wifible). This did not add simultaneous active touch to the same automated run (no human operator present for this pass); touch-under-radio-load and radio-under-serial-load are each independently shown clean, but literally all three at once remains untested. Work item 3's SPI touch-arrangement comparison is resolved by explicit decision rather than further measurement: keep the current software-touch/SPI2-display/SPI3-MicroSD arrangement (established workable, with real headroom, across every session in this record) and defer the realistic alternative (hardware-SPI touch, bit-banged MicroSD) to before V2's SD-backed WiGLE Survey Artifacts — the first feature that needs MicroSD write bandwidth — rather than build and benchmark a software SD driver now against a bus with no measured deficiency, at the cost of a destructive raw-sector write to physical test hardware. ## Outcome

A measured integrated build demonstrates that radio observation, UI/touch, USB traffic, and flash activity can coexist within a defensible MVP resource budget.

## Ownership and inputs

Own the combined feasibility harness, bounded radio probes, instrumentation, and `hardware/profiles/lcdwiki-esp32-32e-2.8/development/feasibility.md`. [F08a](F08a.md) owns the representative UI capacity slice and its independent runtime budget evidence. Coordinate any driver changes with F05–F07 owners. Consume [M1a](../../IMPLEMENTATION_PLAN.md) and [performance budgets](../mvp-validation.md).

## Work

1. Exercise passive WiFi and BLE separately and with explicit switching while rendering, touching, receiving representative complete-snapshot traffic, and writing flash. Keep capture payloads transient.
2. Measure switching gaps, revisit timing, observable loss/uncertainty, touch latency, animation behavior, CPU load, peak/minimum free RAM, and image size across idle and busy conditions. Distinguish measurement limits from receiver guarantees.
3. Resolve the three physical SPI buses against available controllers; compare candidate touch arrangements under combined load.
4. Produce byte budgets for firmware, buffers, NVS, maximum Alert/Baseline records, journal reclamation, and Operational/Capacity-pressure reservations. State checkpoint/write/endurance assumptions and safe provisional counts.
5. Record pass/fail against the declared performance method and required headroom. Resolve failures or revise scope explicitly before passing; add missing evidence to the gate rather than moving it downstream silently.

The current radio/UI capacity block is recorded in the board [feasibility
record](../../hardware/profiles/lcdwiki-esp32-32e-2.8/development/feasibility.md).
Complete [F08a](F08a.md) to establish the bounded operational-UI budget before
choosing the capacity path and resuming the combined physical run.

## Acceptance

- Results identify hardware, dependency/build versions, radio load, instrument method, UART load, coverage limits, and exact test conditions.
- Requested radio windows are not automatically counted as verified receive time; loss and uncertain intervals remain visible.
- One-second complete snapshots have measured serial headroom under a documented size estimate, to be rechecked with C01/TB02's actual messages.
- Partition/RAM budgets justify the proposed retained counts; 32/128/512 remain adjustable, with confirmed assumptions handed to later tickets.
- The board remains recoverable after the test. Passing M1a is a prerequisite for every production protocol/domain tracer ticket.

## Verification and handoff

Run `./dev check all` and `./dev run hardware -- feasibility --port "$CYD_PORT"`. Record physical operator actions, measurement logs, budget table, pass/fail rationale, and integrated commit. Simulator output alone cannot close this ticket. When radio reference equipment or measurement evidence is missing, keep the gate open and name the missing measurement.

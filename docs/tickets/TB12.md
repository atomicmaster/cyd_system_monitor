## Outcome

A qualifying observed deauthentication/disassociation pattern creates an inspectable Alert, can be acknowledged, and ends only through observed recovery or an explicit configuration change.

## Proposed ownership

Own the initial shared C++ episode/rule interface, deauthentication rule, Alert list/detail/banner/LED integration, and first Alert scenarios. BLE rule owners later consume this interface. Persistence implementation belongs to TB13.

## Scope

Define and implement eligibility, minimum observed duration/count, Confidence, Low/Medium/High constraints, episode provenance, peak evidence, acknowledgment, and quiet recovery. Host-targeted High requires relevant fresh captured evidence; retained Host impact never creates Extreme. Expose the journal adapter seam using a bounded volatile adapter.

## Resolve before promotion

Publish rule-specific semantics before writing expected results; label threshold candidates until measurement validates them. Define record sizes with TB13, capacity-pressure evidence hooks, Alert sorting when Operational Alerts have no Confidence, and timing/clock uncertainty behavior.

## Acceptance outline

- Boundary and benign roaming/disconnect fixtures have justified outcomes.
- Coverage Gaps pause evidence/recovery and show unassessable state.
- Acknowledgment does not end or delete an episode; first/last/peak evidence remains inspectable.
- A live rule and replay use identical C++ logic and never emit Extreme.
- Volatile persistence is explicitly interim; this ticket alone does not satisfy durable-history release criteria.

## Verification to specify

Use shared-domain boundary/recovery/acknowledgment replay, UI fixtures, and physical replay of controlled evidence without transmitting disruptive frames. Record exact fixture/scenario names, commands, and evidence paths when promoting this ticket.

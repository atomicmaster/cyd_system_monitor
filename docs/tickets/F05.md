# F05 — Boot the board into a visible diagnostic screen

- **Kind:** Hardware tracer bullet
- **Detail:** Executable
- **Status:** Awaiting hardware
- **Milestones:** M1
- **Depends on:** [F04](F04.md)
- **Board:** Exclusive E32R28T session

Read [dispatch and completion rules](README.md#dispatch-and-completion) before starting. Command names below are planned deliverables, not tools that already exist.

## Outcome

Power on the connected board and see a stable landscape diagnostic screen with profile/build identity, UART output, and reset reason.

## Ownership and inputs

Own `firmware/platform/esp32/display/`, the initial board-startup adapter, `firmware/ui/diagnostic/`, `tools/dev/hardware.sh`, and profile smoke documentation. Consume F02 build targets and the profile pin/capability data. Reserve touch, storage, and radio modules for later tickets. This ticket also pins the LVGL version and wires it into both the ESP32 and desktop builds: F02 left it unpinned because `firmware/ui/` had nothing to render yet.

## Work

1. Pin LVGL (version, integration mode, and any desktop-rendering backend it needs) and record the pin and dependency notice alongside the other F02 pins.
2. Implement profile-driven display/backlight, UART, and reset-reason support with a minimal LVGL diagnostic view.
3. Add an explicit board runner: `./dev run hardware -- <case> --port <path>`. Document port selection, flashing, and manual BOOT/RESET steps; claiming the board is required before running it.
4. Exercise display orientation, repeated reset/boot, and backlight behavior. Record observed exceptions against vendor claims.

## Acceptance

- The physical display renders readable 320×240 diagnostics after boot and reset.
- Application code reads profile capabilities rather than duplicating board-name branches or pin constants.
- Firmware reports the actual build/profile and reset reason over UART.
- Documented ROM bootloader recovery restores the diagnostic image when normal startup is unavailable.

## Verification and handoff

Run `./dev check firmware` and `./dev run hardware -- display-smoke --port "$CYD_PORT"` after selecting the actual device path. Record build identity, board profile, observed display results, and recovery steps. Release the serial port and board claim before F06 or F07 uses them.

## Evidence

Base commit `b2e2e4e`. No physical E32R28T board is available in this environment, so this ticket implements every piece of code, driver, and tooling a human with board access needs, and records exactly what could and could not be verified here. It is **not** marked Done: physical display/reset/backlight evidence is unproduced, per the constraint against fabricating hardware test results.

**Implemented and integrated:**
- LVGL v9.2.2 pinned: ESP32 side via `firmware/platform/esp32/idf_component.yml` (managed `lvgl/lvgl` component) and `firmware/ui/idf_component.yml`; desktop side via CMake `FetchContent` in `simulator/CMakeLists.txt` (tag verified to exist on `lvgl/lvgl` via `git ls-remote`). Recorded in `docs/development.md`'s prerequisites table and `THIRD_PARTY_NOTICES.md`.
- `firmware/tools/generate_profile_header.py` extended to emit display SPI/backlight pin constants (`kDisplayCs/Dc/Sclk/Mosi/Miso/Backlight`) alongside the F06/F07 fields (see F06/F07 Evidence).
- `firmware/platform/esp32/display/`: ILI9341V init over SPI2, landscape orientation via `esp_lcd_panel_swap_xy`/`mirror`, backlight via `ledc` PWM (full-on, dimming-ready), an LVGL flush callback bridging to `esp_lcd_panel_draw_bitmap`.
- `firmware/platform/esp32/reset_reason/`: adapts `esp_reset_reason()` to `firmware::domain::ResetReason`.
- `firmware/platform/esp32/board_init.{hpp,cpp}`: orchestrates NVS init, display, touch, MicroSD, LED, audio, battery, button, reset reason, and the dev console at boot; builds a `firmware::domain::DiagnosticState`; documents the provisional SPI-bus arrangement centrally (display on SPI2, MicroSD+expansion shared on SPI3, touch bit-banged).
- `firmware/ui/diagnostic/`: `BuildDiagnosticScreen()` renders profile id, build identity, reset reason, and a scrollable peripheral list; landscape 320x240.
- `firmware/main/main.cpp`: calls board init, builds the diagnostic or calibration screen depending on whether a valid calibration record is already stored (see F06's Evidence for the full boot-path wiring), pumps `lv_timer_handler()`, logs build identity/profile/reset reason via `ESP_LOGI`.
- Component-name fix: `idf_component_register` names a component after its containing directory, so registering directly from `firmware/platform/esp32/` would have named it `esp32`, colliding with ESP-IDF's own built-in `esp32` chip-support component (ld scripts, ROM bindings) -- `EXTRA_COMPONENT_DIRS` entries take priority in ESP-IDF's component search and would have silently shadowed it, breaking the build. Caught during review; fixed by moving the actual `CMakeLists.txt`/`idf_component.yml` registration into `firmware/platform/esp32/esp32_platform/` (sources stay in their ticket-owned `../display/`, `../touch/`, etc. directories; only the registration point moved), and updating `firmware/CMakeLists.txt`'s `EXTRA_COMPONENT_DIRS` and `firmware/main/CMakeLists.txt`'s `REQUIRES` accordingly.
- `tools/dev/hardware.sh` + `./dev`'s `TARGETS`: `doctor`/`build`/`check` delegate to `firmware.sh`; `run` requires an existing `--port` and a case name, flashes+monitors via `idf.py -p "$port" flash monitor` (no firmware-side case switch -- see the script's comment for why), and refuses to proceed with a nonexistent port.
- `hardware/profiles/lcdwiki-esp32-32e-2.8/development/README.md`: build/flash/monitor commands, BOOT/RESET ROM-bootloader recovery sequence, and a smoke-test checklist.

**Native/simulator checks run and passing:**
- `python3 firmware/tools/test_generate_profile_header.py` -- 7 tests, OK (includes new display-pin assertions).
- `./dev check firmware` -- native CMake/Ninja build + `firmware_domain_tests`, `firmware_domain_calibration_tests`, and `firmware_domain_diagnostic_tests`, all `ok`.
- `./dev build simulator` -- builds `simulator` linked against `firmware_domain`, `firmware_ui`, and FetchContent'd LVGL v9.2.2 (headless, software renderer, no SDL/X11; `LV_BUILD_EXAMPLES`/`LV_BUILD_DEMOS` off and the FetchContent declaration uses `EXCLUDE_FROM_ALL` to keep LVGL's own demo/example targets out of the default build).
- `./dev run simulator -- display-smoke` -- `simulator display-smoke: ok` (builds the diagnostic screen from a fixture `DiagnosticState`, asserts profile/build/reset-reason label text, peripheral row count, and that the recalibrate button is offered only when the fixture reports touch present, via `lv_label_get_text`/`lv_obj_get_child_count`).

**Not attempted:** `idf.py build` / `./dev build firmware` / `./dev build hardware` -- `which idf.py` found nothing and `$IDF_PATH` is unset in this environment; no ESP-IDF toolchain is installed here. The ESP32-only code under `firmware/platform/esp32/` (display, and everything else board_init.cpp orchestrates) is therefore syntactically/logically reviewed against ESP-IDF v5.3 APIs but not compiler-verified.

**Unverified pending physical board access** (F05 acceptance bullets):
- "The physical display renders readable 320x240 diagnostics after boot and reset" -- no display exists to observe.
- "Firmware reports the actual build/profile and reset reason over UART" -- `ESP_LOGI` call sites exist and are reviewed, but no real UART output has been captured.
- "Documented ROM bootloader recovery restores the diagnostic image when normal startup is unavailable" -- the BOOT/RESET sequence is documented from standard ESP32 ROM-bootloader behavior, not exercised on this board.
- Repeated reset/boot and backlight behavior "exceptions against vendor claims" -- nothing has been observed yet to compare against vendor claims.

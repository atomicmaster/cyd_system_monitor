# F05 — Boot the board into a visible diagnostic screen

- **Kind:** Hardware tracer bullet
- **Detail:** Executable
- **Status:** Awaiting hardware
- **Milestones:** M1
- **Depends on:** [F04](F04.md)
- **Board:** Exclusive E32R28T session

Read [dispatch and completion rules](README.md#dispatch-and-completion) before starting. Command names below are planned deliverables, not tools that already exist.

## Outcome

Power on the connected board and see a stable landscape diagnostic screen with profile/build identity, UART output, and reset reason.

## Ownership and inputs

Own `firmware/platform/esp32/display/`, the initial board-startup adapter, `firmware/ui/diagnostic/`, `tools/dev/hardware.sh`, and profile smoke documentation. Consume F02 build targets and the profile pin/capability data. Reserve touch, storage, and radio modules for later tickets. This ticket also pins the LVGL version and wires it into both the ESP32 and desktop builds: F02 left it unpinned because `firmware/ui/` had nothing to render yet.

## Work

1. Pin LVGL (version, integration mode, and any desktop-rendering backend it needs) and record the pin and dependency notice alongside the other F02 pins.
2. Implement profile-driven display/backlight, UART, and reset-reason support with a minimal LVGL diagnostic view.
3. Add an explicit board runner: `./dev run hardware -- <case> --port <path>`. Document port selection, flashing, and manual BOOT/RESET steps; claiming the board is required before running it.
4. Exercise display orientation, repeated reset/boot, and backlight behavior. Record observed exceptions against vendor claims.

## Acceptance

- The physical display renders readable 320×240 diagnostics after boot and reset.
- Application code reads profile capabilities rather than duplicating board-name branches or pin constants.
- Firmware reports the actual build/profile and reset reason over UART.
- Documented ROM bootloader recovery restores the diagnostic image when normal startup is unavailable.

## Verification and handoff

Run `./dev check firmware` and `./dev run hardware -- display-smoke --port "$CYD_PORT"` after selecting the actual device path. Record build identity, board profile, observed display results, and recovery steps. Release the serial port and board claim before F06 or F07 uses them.

**Update:** ESP-IDF v5.3.2 was subsequently found already checked out at `~/esp/esp-idf` on this machine (just not sourced into the shell) and `source ~/esp/esp-idf/export.sh && ./dev build firmware` was run for real. It caught two genuine compiler errors the earlier "reviewed but not compiler-verified" pass had missed -- both fixed and reverified:
- `firmware/domain/CMakeLists.txt` used `CMAKE_CURRENT_SOURCE_DIR` to resolve `calibration/CMakeLists.txt`'s path; ESP-IDF's early component-requirements scan evaluates each component's `CMakeLists.txt` via a throwaway `include()` (not `add_subdirectory()`), which left that variable pointing at the build directory instead of the component's own directory, so the `include()` failed outright ("include could not find requested file"). Fixed by switching every path in that file to `CMAKE_CURRENT_LIST_DIR`, which tracks the actual file being processed regardless of how it was reached.
- `firmware/platform/esp32/display/display.cpp` used `reinterpret_cast` to convert `spi_host_device_t` (an enum) to `esp_lcd_spi_bus_handle_t` (`typedef int`); GCC rejects that as an invalid cast since neither side is a pointer. Fixed to `static_cast`, the correct conversion for an enum-to-integral value (not a bit-reinterpretation).
- Also fixed: `firmware/sdkconfig.defaults` gained `CONFIG_LV_BUILD_EXAMPLES=n` -- the managed `lvgl/lvgl` component's Kconfig defaults that to "on", which was compiling LVGL's entire unused `examples/` tree into the image build for no reason. `tools/dev/firmware.sh`'s `_check_format` was also fixed to exclude `managed_components/` (vendored third-party sources fetched by the component manager, which this project doesn't own the formatting of) after it started scanning them once they existed on disk.

`./dev build firmware` now succeeds end-to-end from a clean `firmware/build/`: `cyd_system_monitor_firmware.bin` is 590200 bytes (44% of the 1MB app partition free; DRAM 57.85% used, IRAM 48.26% used). This is a real compiler/linker pass, not a review -- it does not substitute for the physical acceptance bullets below, which still need the actual board.

**First physical flash session (operator-reported, 2026-09-16):** flashing and monitoring the image above on the real board surfaced two real bugs neither the native/simulator checks nor the compiler pass could catch:
- **Task watchdog crash.** `firmware/platform/esp32/dev_console/dev_console.cpp` called `uart_read_bytes()` (the ring-buffer `driver/uart.h` API) on UART0, which is already owned by ESP-IDF's console/log VFS layer (`ESP_LOGI`, `idf.py monitor`) and never has `uart_driver_install()` called for it. Every call failed instantly instead of blocking, spinning the dev-console task at full speed and starving the IDLE1 watchdog reset (`E (...) task_wdt: Task watchdog got triggered ... IDLE1`, backtrace through `dev_console.cpp:31`). Fixed by reading through `getchar()`/stdin instead, which uses the console VFS driver already installed on UART0 rather than fighting it for ownership of the port.
- **Stalled/garbled display.** The screen rendered once but did not refresh correctly afterward (photographed: overlapping/ghosted calibration-target text). Root cause: `firmware/ui/lv_conf.h` sets `LV_TICK_CUSTOM 0`, which requires the app to supply LVGL's tick via `lv_tick_set_cb()`/`lv_tick_inc()` -- neither was ever called anywhere in `firmware/` or `simulator/`. Without a real tick, `lv_timer_handler()`'s internal refresh-period timer never sees genuine elapsed time. Fixed by calling `lv_tick_set_cb()` in `main.cpp` right after `lv_init()`, wrapping `esp_timer_get_time() / 1000` (the exact ESP32 porting glue LVGL's own vendored docs recommend). Note this gap was invisible to `./dev run simulator`: `simulator/src/lvgl_env.cpp`'s `RenderOnce()` calls `lv_refr_now()` directly, bypassing the timer/tick-gated refresh path entirely, so the simulator never actually exercised the code path this bug lived in.

Both fixes were reflashed and reverified in the same session: captured UART output over 15-20s post-flash showed no `uart_read_bytes`/task_wdt errors (crash fixed), `fw.board_init`/`fw.main` logged `profile=lcdwiki-esp32-32e-2.8 build=esp32-dev-build reset_reason=power-on` cleanly, `ili9341: LCD panel create success` confirmed panel init, and `vfs_fat_sdmmc: sdmmc_card_init failed (0x107)` (`ESP_ERR_TIMEOUT`, no card inserted) confirmed as the expected non-fatal absent-SD path, not a crash.

The display fix (real tick source) resolved the stall, but the reflashed screen still showed a real, distinct second bug: legible-but-sheared/doubled text with green-tinted pixel fringing. Root cause -- `esp_lcd_panel_draw_bitmap`'s SPI backend queues the pixel-data transaction asynchronously (`spi_device_queue_trans`, confirmed in `esp_lcd_panel_io_spi.c`); `FlushCallback` was calling `lv_display_flush_ready()` immediately after `draw_bitmap` returned, before the DMA transaction actually completed, letting LVGL's single (non-double-buffered) draw buffer get overwritten by the next partial render while the SPI DMA was still reading the old contents -- a genuine race, not a rendering-timing issue. Fixed by registering `esp_lcd_panel_io_register_event_callbacks`'s `on_color_trans_done` and calling `lv_display_flush_ready()` from there instead, the driver's real completion signal. The green fringing was a second, independent bug: `firmware/ui/lv_conf.h` never set `LV_COLOR_16_SWAP`, so LVGL's little-endian RGB565 buffer went to the panel without the byte swap ILI9341-over-SPI needs, scrambling blended/anti-aliased font-edge pixel values. Fixed by setting `LV_COLOR_16_SWAP 1`, which `lv_refr.c` uses to call `lv_draw_sw_rgb565_swap()` automatically before `flush_cb`.

Reflashed again: text rendered crisp, single, and color-correct, confirmed by the operator. The final remaining defect was the image reading mirrored/backwards -- `esp_lcd_panel_mirror(g_panel, false, true)`'s MADCTL MX/MY bits were wrong for this panel's physical mounting. `mirror(true, false)` (the other MX-XOR-MY combination) was also observed mirrored. `mirror(true, true)` (the MX-equals-MY pairing) fixed it: operator confirmed correct, non-mirrored text and the USB connector on their preferred side after this exact change, with no further flash needed. `mirror(false, false)` is this orientation's 180-degree-rotated counterpart (see [docs/roadmap.md](../roadmap.md)'s new V1 Settings-configurable landscape flip, captured directly from this finding).

**Unverified pending physical board access** (F05 acceptance bullets):

Both screens share the identical display/flush/LVGL path this session fixed, so the diagnostic screen is expected to render correctly too, but that is an inference, not a direct observation -- reaching it requires the operator to actually complete the 5-point guided calibration + 4-point validation (F06's own checklist), which is the natural next physical session.

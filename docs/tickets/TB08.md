# TB08 — Run the Host as a per-user service with setup status

- **Kind:** Tracer bullet
- **Detail:** Executable
- **Status:** Awaiting hardware — the daemon, the control IPC, the LaunchAgent lifecycle (against a fake `launchctl`), the setup app's logic and provider client, and their tests pass on the desktop (working tree, not yet committed). Nothing was installed into the real `~/Library/LaunchAgents` or loaded into launchd, and no Location or WiFi API was called. Remaining human and physical steps are listed at the end.
- **Milestones:** M3, M4
- **Depends on:** [C02](C02.md)
- **Board:** Exclusive pairing/service integration session

Read [dispatch and completion rules](README.md#dispatch-and-completion).

## Outcome

The Operator starts the Host service from CLI/setup, pairs the display, and sees service and optional WiFi permission status while monitoring survives closing ordinary setup views.

## Design (as built)

- **One serial owner.** `cyd-hostd` (`host/daemon`) owns the port, the one-second complete-snapshot loop, the WiFi-context provider socket and the control socket. Its logic lives in the new `host/hostcore` crate, shared with the CLI: the session runner moved out of `host/cli/src/link.rs` (now `hostcore/src/link.rs`, generalised over a `Channel` trait so a scripted device can stand in for the serial port), plus the identity store, the lock, the control server, the supervisor and the rotating log. `cyd-host run` keeps its behaviour and prints.
- **Exclusive lock.** An `flock` on `<run dir>/daemon.lock`, taken by the daemon and by any CLI command that would open the port. A second holder refuses with the holder's pid. While the daemon runs, `cyd-host unpair|reset-calibration|forget` go through it and `cyd-host run` refuses.
- **Control IPC.** Same-user `0600` socket in a `0700` directory, versioned bounded JSON lines, `status`, `monitors`, `pair_start`, `pair_cancel`, `unpair`, `reset_calibration`, `forget`, `stop`. Full schema, drop counters and restart semantics: [host-control-ipc.md](../host-control-ipc.md).
- **Pairing is explicit.** A plugged-in unpaired display is not touched until `pair_start`. The confirmation is the touch on the display showing the same code (the protocol has no Host-side confirmation, so there is no `pair_confirm`). Refusals park the port so the ESP32 is not reset in a loop.
- **Resync.** Reconnect after unplug, a link error, or a gap over 5 s on the wall clock or the sleep-inclusive monotonic clock (sleep/wake, which also re-baselines every rate and re-reads cached slow sources) always negotiates a fresh session and sends an immediate complete snapshot; the daemon never exits because a provider, a permission or the setup app is absent.
- **Service.** `cyd-host service install|uninstall|start|stop|restart|status` (`host/cli/src/service.rs`) generates the LaunchAgent plist (`RunAtLoad`, `KeepAlive/SuccessfulExit=false` so a crash restarts but a clean stop does not, `ProcessType Adaptive`, `LimitLoadToSessionType Aqua`, no root) and drives `launchctl bootstrap|bootout|kickstart|print gui/<uid>` through a `Launchctl` trait. `--dry-run` prints the plist and changes nothing. Uninstall removes only the plist and the registration.
- **Logs.** The daemon writes `~/Library/Logs/CYD System Monitor/hostd.log` itself (state changes only) and rotates at 50 MiB or 7 days, keeping one previous file; launchd's own stdout/stderr file only receives crash output and is not rotated.
- **Setup app.** `macos/setup-app`: library `SetupCore` (models, permission mapping, provider protocol and runner, bounded socket client, status text) with Swift Testing tests, and a thin SwiftUI `SetupApp`. It shows service, daemon, pairing and permission state, offers start/cancel pairing and unpair, prints the disclosure verbatim above the only button that can request Location permission, and runs the provider client that connects to the daemon's provider socket. Closing it costs only the optional context: the daemon degrades it to unavailable within 15 s.
- **Who supplies Association Context after setup closes:** nobody. The provider is the setup app (or, later, a helper it owns); when it stops, the context is reported unavailable, truthfully, and everything else continues.

## Acceptance and commands

- `./dev check host` (rustfmt, clippy `-D warnings`, all tests), `./dev check macos` (`swift build`, `swift test`), `./dev check protocol`, `./dev check firmware`, `./dev check simulator` pass.
- `cargo test -p hostcore --test daemon` (needs `firmware/domain/tests/build/link_cli` from `./dev check firmware`): status through no device, pairing required, pairing with a matching code, paired; a second daemon refused with the first's pid; provider silence and disconnect degrade the context after 15 s (injectable clock); 30 abusive status clients closing and reopening leave one session and a running snapshot loop; unplug/replug and sleep/wake each produce a new session with snapshots resuming; unpair forgets only the stored display; `stop` exits cleanly and releases the sockets and lock.
- `cargo test -p hostcore control` and `-p hostcore lock|logging`: malformed, oversized, unversioned, wrong-uid and flooding input dropped and counted; modes; rotation.
- `cargo test -p cli service`: golden plist (`host/cli/fixtures/service/hostd.plist`), fake launchctl install/start/stop/restart/status, uninstall keeps identity/logs/daemon, dry run writes nothing, refusal of a missing daemon.
- `swift test` in `macos/setup-app`: verbatim disclosure (checked against `docs/macos-components.md`), Location-to-permission and permission-to-availability tables, request gating, exact provider lines and session policy (permission after hello, heartbeat each second, change sent at once, `seq` strictly increasing, SSID/BSSID only when `available`), status decoding of real daemon output, private-path refusal, oversize and timeout, the provider runner against a scripted daemon socket.
- By hand, no device: `CYD_RUN_DIR=$(mktemp -d) CYD_HOME=$(mktemp -d) cyd-hostd --log-dir <tmp> &` then `cyd-host status`, `cyd-host stop`; `cyd-host service install --dry-run --daemon-path /abs/cyd-hostd`.

## Departures from the outline

- Provider and control sockets are separate; the control socket has no provider role.
- No `pair_confirm` command (see above); no incremental status streaming (clients poll `status`).
- Swift tests use Swift Testing: XCTest is not present without Xcode. With only the Command Line Tools the default build system does not hand the compiler the Testing macro plugin, so `Package.swift` adds its directory explicitly when it exists. `@State` is likewise unusable without Xcode's SwiftUIMacros plugin, so view state lives in the model.
- The launchd label `com.cydsystemmonitor.hostd` is a placeholder until R01 sets the product identifier.
- Serial discovery (`/dev/cu.usbserial*`, `usbmodem*`, `wchusbserial*`, `SLAB_USBtoUART`) is unverified on hardware; with several candidates the daemon waits for a named `--port` or `pair_start` port.

## Remaining human and physical steps

1. **Development signing.** Build the setup app as a signed `.app` (Xcode project or `codesign`) with an `Info.plist` carrying `NSLocationWhenInUseUsageDescription` and the sandbox-off or Location entitlement the chosen signing needs. A bare SwiftPM executable has no bundle, so macOS shows no Location prompt for it. Notarization and the final identifier stay in R01.
2. **Location consent prompt.** An Operator clicks "Request Location permission" in the signed app once and answers the macOS prompt; record granted, then denied (System Settings), and confirm the display and `cyd-host status` show `granted` with the real availability (`available` or `authorized_unavailable`) and `denied`. This closes the TB05/R03 integration gate.
3. **Real LaunchAgent install.** `cyd-host service install --daemon-path <abs path>`, log out and in, confirm `service status` is running; `kill -9` the daemon and confirm launchd restarts it; `cyd-host stop` and confirm it stays stopped; `service uninstall` and confirm only the plist went away (identity, logs kept). Check `hostd.log` rotation on a real long run if desired.
4. **Sleep/wake on hardware.** Sleep the Mac with the display attached for over a minute and confirm the display resumes live data on a new session without a touch.
5. **Physical pairing and status smoke.** With a flashed board: `cyd-host pair`, confirm the shown code on the touchscreen, watch `cyd-host status` reach `paired_connected`, unplug and replug, `cyd-host unpair`, and confirm the setup app shows the same states while open and after being closed and reopened.
6. **Serial discovery** on a real board (which node the CH340/CP210x bridge creates on macOS 26).

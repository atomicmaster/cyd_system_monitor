## Outcome

The Operator starts the Host service from CLI/setup, pairs the display, and sees service and optional WiFi permission status while monitoring survives closing ordinary setup views.

## Proposed ownership

Own LaunchAgent management, Host local status/control IPC, SwiftUI setup/pairing/permission modules, and service integration fixtures. TB02 owns the established transport; coordinate lifecycle hooks through its interfaces.

## Scope

Implement install/start/stop/restart/status for the per-user daemon and the minimal setup application. Add foreground disclosure/optional permission for WiFi identity. Define who supplies continuing Association Context after setup UI closes, including its truthful unavailable state if the provider stops.

## Resolve before promotion

Agree provider/control IPC and ownership with TB05; define restricted local access, restart semantics, and single serial-port ownership. Identify development signing and OS consent actions requiring an Operator. Release notarization stays in R01.

## Acceptance outline

- Closing/reopening setup does not stop ordinary Host Metrics or duplicate daemon/USB owners.
- Permission denial or unavailable context does not block monitoring.
- Service restart/sleep/wake resynchronizes complete snapshots; unpairing is explicit and preserves histories.
- Real granted/denied context integrates with TB05 before release; no privileged helper is installed.

## Verification to specify

Use Host IPC/service fixtures, Swift checks, service lifecycle runs, and physical pairing/status smoke. Record Operator consent steps separately. Record exact fixture/scenario names, commands, and evidence paths when promoting this ticket.

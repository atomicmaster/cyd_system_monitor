# F07 — Exercise the remaining board peripherals

- **Kind:** Hardware feasibility
- **Detail:** Executable
- **Status:** Blocked (missing a speaker to verify audio output, and expansion-signal test equipment for GPIO35)
- **Milestones:** M1
- **Depends on:** [F05](F05.md)
- **Board:** Exclusive E32R28T session

Read [dispatch and completion rules](README.md#dispatch-and-completion) before starting. Command names below are planned deliverables, not tools that already exist.

## Outcome

The diagnostic image exercises the remaining profile capabilities and distinguishes measured behavior from vendor claims before combined-load validation.

## Ownership and inputs

Own RGB LED, audio-enable/DAC, MicroSD probe, battery-ADC diagnostic, button/expansion probe adapters, and their profile evidence. F06 owns touch/calibration. Both consume the diagnostic screen through separate diagnostic modules; the integration owner registers them serially.

## Work

1. Exercise each remaining vendor-claimed pin safely in its documented role, respecting input-only and boot-strapping constraints.
2. Verify GPIO4 amplifier-enable behavior on the fitted board and exercise optional sound deliberately; its product default remains off.
3. Probe MicroSD and shared expansion SPI, record the provisional bus allocation, and expose board voltage as diagnostic data only.
4. Record reset/button behavior and equipment/operator steps needed to validate expansion signals. An unexercised pin remains an open result, not a passed claim.

## Acceptance

- LEDs, optional audio, storage presence/failure, and ADC diagnostics are visible and reproducible.
- Missing SD is an ordinary idle status; the MVP does not acquire an SD dependency for normal operation.
- Calibration work from F06 remains intact after integration.
- M1 has evidence for every promised peripheral or an explicit resolved profile exception; remaining unverified hardware prevents declaring M1 complete.

## Verification and handoff

Run `./dev check firmware` and `./dev run hardware -- peripherals --port "$CYD_PORT"`. Attach the pin/capability result table, build identity, and optional external-equipment steps. F06 and F07 may develop in parallel, but flashing, port use, and diagnostic registration are serialized.

## Evidence

Base commit `b2e2e4e`. This ticket's code was first implemented with no physical board available (see F05's Evidence section for that environment). A later physical session (recorded below) exercised every peripheral for which equipment was available -- LED, battery, BOOT button, and MicroSD (all three of absent/unreadable/mounted) are all confirmed. This ticket is **not** marked Done: it is **Blocked** on two specific missing inputs -- a speaker to verify audio's acoustic output, and expansion-signal test equipment for GPIO35 -- both explicitly recorded rather than silently skipped.

**Implemented and integrated:**
- `firmware/tools/generate_profile_header.py` extended to emit `rgb_led` (red/green/blue/active_low), `microsd` (cs/mosi/sclk/miso), `expansion_spi.cs`, `audio` (enable/enable_active_low/dac/alert_sound_default), `battery.adc`, `buttons.download`, `uart0` (rx/tx), and `expansion.input_only` as generated constants.
- `firmware/platform/esp32/led/`: three `ledc` PWM channels on the profile's RGB pins, with `SetColor()` accepting 0-255 brightness regardless of the active-low wiring (duty inversion handled internally).
- `firmware/platform/esp32/audio/`: enable-pin GPIO (respecting `enable_active_low`), a `dac_oneshot` channel on the profile's DAC pin, and a simple blocking square-wave `PlayTestTone()`; amplifier starts disabled and `alert_sound_default` stays off, matching the profile's stated default.
- `firmware/platform/esp32/microsd/`: `Probe()` over the shared expansion SPI3 bus via `esp_vfs_fat_sdspi_mount`; absence is reported as a non-fatal `present=false, detail="not present (idle)"` result rather than an error, per "Missing SD is an ordinary idle status."
- `firmware/platform/esp32/battery/`: `adc_oneshot` + `adc_cali` line-fitting read (the ADC calibration scheme the original ESP32 actually supports; see the Update note below) on the profile's ADC pin, exposed only as a raw millivolt diagnostic value (no state-of-charge claim), with an uncalibrated linear fallback if calibration is unavailable.
- `firmware/platform/esp32/button/`: BOOT (GPIO0) configured and read as an input only, never driven, respecting its boot-strapping role.
- `firmware/platform/esp32/board_init.cpp`: registers all of the above into one `DiagnosticState.peripherals` list serially, and centrally documents the provisional SPI-bus allocation (display/SPI2 exclusive; MicroSD+expansion/SPI3 shared; touch bit-banged) so it is one decision point rather than scattered assumptions.
- `simulator/src/fixtures.cpp` + `simulator/src/scenarios/peripherals_scenario.cpp`: a fixture `DiagnosticState` covering touch/rgb_led/microsd(absent)/audio/battery/boot_button/expansion rows, and a scenario that renders them through the real `firmware::ui::diagnostic::BuildDiagnosticScreen` and asserts each row's name/presence/detail text, plus a specific assertion that the fixture's absent MicroSD renders as an ordinary `ABSENT` row rather than an error state.

**Update:** ESP-IDF v5.3.2 was found on this machine and `./dev build firmware` now passes end-to-end (see F05's Evidence). `firmware/platform/esp32/{led,audio,microsd,button}/` compiled cleanly against ESP-IDF v5.3 APIs (`ledc`, `dac_oneshot`, `esp_vfs_fat_sdspi_mount`, `driver/gpio.h`) as originally written. `battery/battery.cpp` did not: it used `adc_cali_curve_fitting_config_t`/`adc_cali_create_scheme_curve_fitting`, which is the ADC calibration v2/v3 "curve fitting" scheme only available on later chips (S2/C3/S3/...) -- the original ESP32 this board uses only has v1 "line fitting" calibration. **Physical session (operator + agent, 2026-09-16):** ESP-IDF v5.3.2 was sourced and `./dev build firmware`/`idf.py flash` used throughout (see F05's Evidence for that environment). `firmware/platform/esp32/dev_console/` gained three commands specifically for this session's on-demand exercises, alongside F06's existing `DEV:CLEAR_CALIBRATION`: `DEV:LED_TEST` (cycles red/green/blue for 800ms each, then off), `DEV:AUDIO_TEST` (deliberately enables the amplifier, plays a 1kHz/500ms tone, disables it again), and `DEV:PERIPHERAL_STATUS` (re-probes MicroSD/battery/BOOT-button live, unlike `board_init.cpp`'s once-at-boot probe, so an operator can change physical state between runs and see the result change). `firmware/main/main.cpp` also gained a boot-time UART dump of the full `DiagnosticState.peripherals` list, so results are captured in log evidence without needing a screen photo for every check.

- **RGB LED**: `DEV:LED_TEST` run twice; operator confirmed visually seeing the red/green/blue/off cycle both times. Confirmed visible and reproducible.
- **Battery/supply ADC**: consistently plausible readings across many boots and `DEV:PERIPHERAL_STATUS` calls (2101-2127mV), never zero or garbage. Confirmed reproducible; still diagnostic-only per the profile's stated scope, no state-of-charge claim.
- **BOOT button**: `DEV:PERIPHERAL_STATUS` correctly read `boot_button_pressed=1` while the operator held it and `=0` after release, confirmed live in both states. Confirmed reproducible.
- **MicroSD**: all three of the driver's designed states confirmed on real cards: absent (`not present (idle)`, `sdmmc_card_init failed (0x107)`/`ESP_ERR_TIMEOUT`, non-fatal), present-but-unreadable (an NTFS-formatted card correctly rejected -- `sdspi_transaction: cmd=5` shows the card responds at the SPI/protocol level, but `esp_vfs_fat_sdspi_mount` correctly fails with `FR_NO_FILESYSTEM`, since ESP-IDF's FatFs does not support NTFS -- confirmed via `diskutil list`/`diskutil info` on the Mac, not a guess), and successfully mounted (a card freshly reformatted to genuine FAT32 via `diskutil eraseDisk MS-DOS ... MBR`, confirmed `MS-DOS FAT32` via `diskutil info` before insertion, mounted cleanly: `microsd_present=1 microsd_detail="mounted"`). All three reproducible on demand via `DEV:PERIPHERAL_STATUS`. "Missing SD is an ordinary idle status" and "M1 does not acquire an SD dependency for normal operation" both directly confirmed -- boot and the diagnostic/calibration screens behaved identically regardless of SD state throughout.

GPIO4's electrical enable/disable behavior is therefore also unconfirmed (no multimeter/scope used either). The SC8002B/FM8002E electrical-limit discrepancy (`audio-amplifier-comparison.md`) remains unresolved against the actual fitted part for the same reason.

# TB09 — Show the real radio schedule and coverage

- **Kind:** Tracer bullet
- **Detail:** Executable
- **Status:** In progress — the host-native scheduler and coverage model are done (see Slice 1); the coverage status line is done in the simulator (Slice 2, with a known worst-case overflow); the ESP32 driver and physical runs are awaiting hardware.
- **Milestones:** M2, M4, M5
- **Depends on:** [C02](C02.md)
- **Board:** Exclusive radio/display load sessions

Read [dispatch and completion rules](README.md#dispatch-and-completion).

## Outcome

WiFi/BLE observation mode changes appear in persistent status with measured gaps while CPU monitoring and touch remain responsive.

## Proposed ownership

Own `firmware/platform/esp32/radio/` scheduling/driver coordination, `firmware/domain/coverage/`, coverage status UI, and scheduler scenarios. TB10/TB11 own protocol-specific frame decoders/views.

## Scope

Turn F08 probes into explicit passive 2.4 GHz WiFi/BLE windows with validated channel defaults, independent radio enable controls, bounded event queues, and coverage/loss accounting. Preserve powered standalone operation.

## Promotion decisions

Candidate defaults, all from F08 evidence and all revisable by M5 measurements:

- **Dwell and revisit:** WiFi dwells 205 ms per channel (two 802.11 beacon periods, the Kismet floor F08 aligned to) over US channels 1-11. With BLE enabled a 205 ms BLE window follows every WiFi dwell, so both radios get equal time and a WiFi channel comes round every 4.5 s. A disabled radio's windows go to the other, so WiFi alone revisits every 2.3 s. The channel list is a scheduling preference (ADR 0026), configurable in place of the default.
- **Receiver availability:** the driver reports `observed_ms` per window. F08 measured a WiFi channel switch under 1 ms and a BLE scan enable of 1.4-5.4 ms, so anything less than half a window observed counts as a Coverage Gap; smaller losses reduce the reported observed share only. Requested window time is never counted as observed.
- **Unknown, not quiet:** a radio with no report for three expected revisit periods reads `no-data`. Only observed time may feed observed-quiet recovery (`CoverageLedger::observed_ms`).
- **Event metadata and overload:** events follow the C02 observation contract in a fixed-size queue that drops the oldest event and counts each drop (`BoundedEventQueue`); the per-window drop count is reported through the ledger and shown in coverage.
- **Disabled and faulted radios:** `operator-disabled` is its own state (not zero activity, not a gap). Both disabled yields no windows and `host_only`. A driver initialisation or runtime fault is recorded with its reason (`fault`) for later Operational Alert integration.
- **Task ownership:** one radio task owns the scheduler: it asks `ObservationScheduler::NextWindow`, drives WiFi/BLE, and reports `WindowReport`s. Parsers (TB10/TB11) only consume events; the UI only reads `CoverageView`.

## Acceptance outline

- UI reports actual schedule/known gaps and uncertainty instead of inferring quiet from scheduled time.
- One disabled radio gives its budget to the other; both disabled allow Host-only monitoring.
- No active scan/probe traffic is intentionally generated; initialization faults are surfaced for later Operational Alert integration.
- Dense traffic/UI/USB stress remains within accepted budgets or reopens the gate.

## Verification to specify

Use deterministic coverage replay plus controlled physical radio/load measurements. Record no-Host-but-powered operation separately from power removal. Record exact fixture/scenario names, commands, and evidence paths when promoting this ticket.

## Slice 1 — scheduler and coverage model (done)

`firmware/domain/coverage.hpp` and `src/coverage.cpp`: `ObservationScheduler`, `CoverageLedger` (bounded gap list, totals, faults), `BoundedEventQueue`, `MakeCoverageView`, and `FormatCoverage`.

- `./dev check firmware` runs `firmware_domain_coverage_tests` (alternation and wraparound, budget reassignment, Host-only, gap versus switching loss, stale-to-unknown, faults, bounded gaps and queue).
- `./dev run simulator -- coverage` replays a scripted driver (lost windows, a disabled radio, a fault, a silent driver, both radios off) and compares `simulator/scenarios/coverage.expected`.

## Slice 2 — coverage status line (done, simulator only)

`CoverageStatusText` renders `CoverageView` as the current (or most recently reported) Observation Window plus each radio's problem state: `WiFi ch6` or `BLE scan` for the radio in its window, `gap` (the latest window lost), `?` (unknown, never quiet), `off`, `fault`, e.g. "WiFi ch6 BLE gap", "WiFi ? BLE off"; "Host only" when both are off. A radio observing normally is not named between its windows. There is no percentage: observed time over requested window time is not capture coverage (with the default plan each WiFi channel is observed for about 4.5% of wall time with BLE on, 9% with WiFi alone), so a share read like continuous capture (`docs/radio-model.md`). `CoverageView::current` names the window's radio; `observed_permille` stays in `CoverageView` and `FormatCoverage` for replay checkpoints. `SystemScreen::Update` takes the text as an optional argument and shows it between the connection and clock labels of the persistent bar. `./dev run simulator -- system-screen` covers unknown, the current window, gap, disabled, Host-only, and a stale Host link; `firmware_domain_coverage_tests` covers the text.

Fit, measured in the simulator's system-screen scenario (Montserrat 14; the bar row is 312 px wide, but the default theme's 13 px padding and 2 px border leave 282 px of content, with two 8 px column gaps): the typical "WiFi ch11" (64 px) fits beside "Connected" and a 12 h clock (221 px), and every coverage text, up to "WiFi fault BLE fault" (139 px), fits beside "Connected" and a 24 h clock (272 px). It does **not** fit in general: "Incompatible Host" (134 px) and "12:58 PM UTC+12:45" (134 px) overflow the bar on their own (284 px); the boot state "Waiting for Host" + "WiFi ? BLE ?" + "Time unavailable" needs 346 px (as it did with the old text); "Connected" + the widest coverage + "12:58 PM" needs 296 px. Proposed smallest honest form, measured but not yet applied: side padding 4 px and no border on the bar row (304 px of content); bar-only short connection words "Waiting", "No Host", "Incompatible" (widest 97 px); the bar clock as "--:--" when unavailable and without its zone suffix (widest "12:58 PM", 60 px; the zone stays on Settings); and `err` for a faulted radio (widest coverage then "WiFi gap BLE gap", 129 px). Worst case 97 + 129 + 60 + 16 = 302 px. Every state stays visible; nothing is truncated. Still to check for readability on the real 320×240 display.

# TB09 — Show the real radio schedule and coverage

- **Kind:** Tracer bullet
- **Detail:** Executable
- **Status:** In progress — the host-native scheduler and coverage model are done (see Slice 1); the radio tray is done in the simulator (Slice 2, fitted to the bar with the Overview redesign; readability on the real display is unchecked); the ESP32 radio task is code-complete and compiles (Slice 3); flashing it and the physical runs are awaiting the board.
- **Milestones:** M2, M4, M5
- **Depends on:** [C02](C02.md)
- **Board:** Exclusive radio/display load sessions

Read [dispatch and completion rules](README.md#dispatch-and-completion).

## Outcome

WiFi/BLE observation mode changes appear in persistent status with measured gaps while CPU monitoring and touch remain responsive.

## Proposed ownership

Own `firmware/platform/esp32/radio/` scheduling/driver coordination, `firmware/domain/coverage/`, coverage status UI, and scheduler scenarios. TB10/TB11 own protocol-specific frame decoders/views.

## Scope

Turn F08 probes into explicit passive 2.4 GHz WiFi/BLE windows with validated channel defaults, independent radio enable controls, bounded event queues, and coverage/loss accounting. Preserve powered standalone operation.

## Promotion decisions

Candidate defaults, all from F08 evidence and all revisable by M5 measurements:

- **Dwell and revisit:** WiFi dwells 205 ms per channel (two 802.11 beacon periods, the Kismet floor F08 aligned to) over US channels 1-11. With BLE enabled a 205 ms BLE window follows every WiFi dwell, so both radios get equal time and a WiFi channel comes round every 4.5 s. A disabled radio's windows go to the other, so WiFi alone revisits every 2.3 s. The channel list is a scheduling preference (ADR 0026), configurable in place of the default.
- **Receiver availability:** the driver reports `observed_ms` per window. F08 measured a WiFi channel switch under 1 ms and a BLE scan enable of 1.4-5.4 ms, so anything less than half a window observed counts as a Coverage Gap; smaller losses reduce the reported observed share only. Requested window time is never counted as observed.
- **Unknown, not quiet:** a radio with no report for three expected revisit periods reads `no-data`. Only observed time may feed observed-quiet recovery, and only through eligible per-window reports (per WiFi channel, zero drops), never the radio-wide `CoverageLedger::observed_ms` totals, which keep partial time from gap windows.
- **Event metadata and overload:** events follow the C02 observation contract in a fixed-size queue that drops the oldest event and counts each drop (`BoundedEventQueue`); the per-window drop count is reported through the ledger and shown in coverage.
- **Disabled and faulted radios:** `operator-disabled` is its own state (not zero activity, not a gap). Both disabled yields no windows and `host_only`. A driver initialisation or runtime fault is recorded with its reason (`fault`) for later Operational Alert integration.
- **Task ownership:** one radio task owns the scheduler: it asks `ObservationScheduler::NextWindow`, drives WiFi/BLE, and reports `WindowReport`s. Parsers (TB10/TB11) only consume events; the UI only reads `CoverageView`.

## Acceptance outline

- UI reports actual schedule/known gaps and uncertainty instead of inferring quiet from scheduled time.
- One disabled radio gives its budget to the other; both disabled allow Host-only monitoring.
- No active scan/probe traffic is intentionally generated; initialization faults are surfaced for later Operational Alert integration.
- Dense traffic/UI/USB stress remains within accepted budgets or reopens the gate.

## Verification to specify

Use deterministic coverage replay plus controlled physical radio/load measurements. Record no-Host-but-powered operation separately from power removal. Record exact fixture/scenario names, commands, and evidence paths when promoting this ticket.

## Slice 2 — radio tray in the status bar (done, simulator only)

`MakeCoverageStatus(CoverageView)` returns a `RadioSlotView` (`RadioSlotState` plus WiFi channel) per radio for the persistent bar: `kScanning` (its window is the current one), `kIdle`, `kOff` (operator-disabled), `kGap` (the latest window lost), `kNoData` (unknown, never idle) and `kFault`; fault, gap, no data and off win over scanning and idle. The WiFi channel is the active window's while scanning, the last observed one while idle, gap or fault, and blank otherwise; BLE has none. Both radios off is both slots off; there is no "Host only" text. There is no percentage: observed time over requested window time is not capture coverage (with the default plan each WiFi channel is observed for about 4.5% of wall time with BLE on, 9% with WiFi alone), so a share read like continuous capture (`docs/radio-model.md`). `CoverageView::current` names the window's radio; `observed_permille` stays in `CoverageView` and `FormatCoverage` for replay checkpoints.

The first board run showed why the earlier single text label ("WiFi ch6" / "BLE scan" in one spot) was wrong: Observation Windows alternate about five times a second, so it looked like blinking. The bar now has a phone-style radio tray beside the clock, each radio in a fixed slot (`docs/ui-design.md`, Persistent status bar): a WiFi icon with a one-character flag box and a fixed 27 px channel box, a drawn BLE rune with a flag box, then a hairline. Colour is the state: WiFi cyan or BLE blue, icon and channel alike, while the radio works (scanning or waiting its turn: following the window read as pulsing on the board, so the colour is steady), muted for a gap (`~`) or unknown (`?`), the text colour with `!` for a fault, and dim (`0x3A4266`) with a slash across the icon when off. Positions never move, and `SystemScreen::Update` touches a widget only when its value changed. `SystemScreen::Update` and `LinkScreen::Update` take the `CoverageStatus`. The WiFi driver's own per-window INFO lines (`ic_enable_sniffer`, `ic_disable_sniffer`, about five a second) are quieted with `esp_log_level_set("wifi", ESP_LOG_WARN)` where WiFi comes up; our `fw.*` tags are untouched. `./dev run simulator -- system-screen` covers every slot state for both radios, Host-only, a stale Host link, fixed positions, and the worst-case fit (280 of 312 px); `firmware_domain_coverage_tests` covers the slot states.

Fit (applied with the Overview redesign; see [ui-design.md](../ui-design.md#persistent-status-bar)): the bar is one 12 pt line with 312 px of content and two 8 px gaps. Its words are shortened to "Waiting", "Incompatible" and `err` for a faulted radio. Its clock has no zone suffix, except `UTC` when the zone is unknown; the "Show timezone" setting is retired, and old records carrying its bit still load. The measured worst case is "Disconnected" (84) + "WiFi gap BLE scan" (111) + "Time unavailable" (101) + 16 = 312 px. `system-screen` now fails if any combination overflows. `Time unavailable` is kept in full, as the design requires. Still to check for readability on the real 320×240 display.

## Slice 3 — ESP32 radio task (code-complete, awaiting board)

Built with ESP-IDF v5.3.2 and linked; **not flashed and not run**. Everything below the domain seam is unmeasured until the physical session.

**What landed** (`firmware/platform/esp32/radio/`, replacing the F08 `controller_probe.*`, which is deleted):

- `hci_transport.*`: the VHCI host callback only copies each H4 packet (with its arrival time) into a bounded FreeRTOS message buffer and counts overflow. It reads the H4 event code, nothing more, to choose between a 4 KiB advertising buffer and a 1 KiB command-event buffer, so an advertising flood cannot evict command completions. The HCI worker task (core 1, priority 5, 3.5 KiB stack) parses with `hci::Parse`: Command Complete/Status go to `hci::Tracker`, advertising reports go to the BLE handler, a Hardware Error raises a flag the next BLE window turns into a `hardware error` fault after a controller reset. Command events that were queued before a controller reset are dropped (and counted as `stale_dropped`), and a Command Status with status 0 never clears an opcode's quarantine, so a late Complete cannot satisfy the next command. The Tracker reserves a send (`TryBeginSend`), the packet is handed to the controller with the mutex released, and `MarkSent` follows; a Complete or rejection for the outstanding opcode that arrived before the reservation or the send time was buffered for an earlier command, is ignored and counted in `stale_dropped`. Commands go through `Tracker::Issue` / `TryBeginSend` under one mutex that is released before `esp_vhci_host_send_packet` is called (BLE modem sleep is off: `CONFIG_BTDM_CTRL_MODEM_SLEEP=n`), with one deadline covering send availability plus completion and no retry loop. The boot runs through `hci::BootSequencer`, checking every completion. On `kNeedsControllerReset`, a failed boot or a Hardware Error the controller is disabled and re-enabled, `Tracker::ResetController` is called and the boot is redone, up to three attempts, then the radio is faulted (`kInit`). No call aborts.
- `wifi_monitor.*`: `WIFI_MODE_NULL`, promiscuous mode, management-frame filter. `Start` enables promiscuous mode, sets the channel and reads it back (a different channel is a `set channel` fault); `Stop` disables promiscuous mode. Frames heard before the window opens are counted outside-window, not kept. The callback builds the provisional `ObservationEvent` (type, subtype, addr2, addr3, length, RSSI, retry/FCS flags) and offers it to the gate. No connect, no scan API, no `esp_wifi_80211_tx`, no network interface.
- `ble_scanner.*`: `LE_Set_Scan_Enable` through the tracker with a checked, bounded completion (500 ms). Scan parameters come from the boot sequence: passive, interval == window == 0x50 (continuous within a window); duplicate filtering is off. A rejected or timed-out command faults the window (`kHciRejected` / `kHciTimeout`); a Stop that fails is retried by the runner's fail-closed loop.
- `observation_gate.*`: the portMUX-guarded open-window record (id, generation, start, deadline, open, plus the window's radio) and the two `EventRing`s (WiFi 128 and BLE 96 events, on a `PortMuxLock`). The window check and the push share one critical section, so no event can enter a ring once `EndWindow` returns. Events with no open window, outside `[start, deadline]`, or from the other radio are counted per protocol, never pushed. `Drain` pops both rings in batches of 8 into a counting sink (per-protocol tally) until the TB10/TB11 parsers exist.
- `radio_driver.*`: `Esp32RadioDriver`. `NowUs` is `esp_timer_get_time`. `WaitUntilUs` blocks in `xTaskNotifyWait` with the timeout rounded up to whole ticks; the control notification bit returns `kControl` and is cleared by the wait.
- `radio_task.*`: the radio task (core 1, priority 4, 8 KiB stack: about 4 KiB of loop plus the unmeasured one-off WiFi/BLE bring-up, to be trimmed from the `stack_free` figure in the init log line) loops `RadioRunner::Step()`. Its `ControlSource` is a queue of `ControlRequest` (enqueueing also notifies the task); its `RadioSink` is a 32-message queue of `RadioMessage`, sized for an app-loop stall of about 3 s at the steady ~10 messages/s. A full queue never blocks the task: the loss is counted, the newest config and per-radio fault state are resent when room returns, and a `kReportQueueOverflow` fault names each radio that lost a window message (withdrawn after eight clean report sends). A radio whose init failed reports a `kInit` fault at its first window and the other radio keeps working. Both tasks are registered with `capacity::RegisterTask`.

**App loop** (`main/main.cpp`): `StartRadio()` replaces `StartControllerOnlyProbe()`; it only creates the queues and tasks, so boot does not wait and nothing depends on calibration or a Host. Every loop iteration `PumpRadio()` drains the message queue, whichever screen is shown and whether or not a Host is linked: `kConfigApplied` updates the effective config (`ToObservationConfig`), `kWindowStarted` sets the `ActiveWindow`, `kWindowReport` goes to `CoverageLedger::Record` and clears the matching `ActiveWindow`, `kFault` / `kFaultCleared` set and clear the ledger fault (`FaultText`). `DrawMonitor` passes `MakeCoverageStatus(MakeCoverageView(config, ledger, now_ms, active))` to `LinkScreen::Update`, with `now_ms` from `esp_timer` (the clock of the reports). The initial configuration is both radios on with the default plan; it is not persisted (TB16).

**Dev console**: `DEV:HCI_STATUS`, `DEV:CHANNEL_STATUS` and `DEV:BLE_TOGGLE_STATUS` are gone. `DEV:RADIO_STATUS` prints the effective config and generation, the active and last completed window, per-radio ledger totals and fault reasons, per-protocol event counts, outside-window and wrong-radio counts, ring drops (total and unattributed), report and control queue overflows, VHCI rx-buffer overflows, HCI timeouts/rejections/late/unexpected/malformed, credit, controller resets, and the radio and HCI worker stack headroom. `DEV:RADIO_WIFI_ON`, `DEV:RADIO_WIFI_OFF`, `DEV:RADIO_BLE_ON` and `DEV:RADIO_BLE_OFF` enqueue a `ControlRequest` (a thread-safe queue; the console touches no app-loop state). The console reads the app loop's ledger and window state from a copy the app loop publishes after each batch of messages. DEV commands are not parsed once `CYD:LINK` has activated; reset the board to get the console back.

**Build** (`idf.py -B <fresh dir> build`, ESP-IDF v5.3.2, exit 0, no warnings in our sources): `sdkconfig.defaults` now carries the product radio settings: controller-only BLE (VHCI, no NimBLE or Bluedroid), BLE-only controller mode, passive WiFi, software coexistence, the BLE controller on core 0 and the WiFi task on core 1, the custom 4 MB partition table. The image is 1,270,288 B in the 2 MiB (2,097,152 B) `factory` partition (39% free). Static DRAM is 54,488 B used with 70,092 B remaining (the LVGL pool and draw buffer are on the heap; the rings, queues and message buffers are allocated at start, not linked statically). IRAM is 113,026 B used with 18,046 B remaining (86%), so the WiFi IRAM options (`ESP_WIFI_IRAM_OPT`, `ESP_WIFI_RX_IRAM_OPT`) stay off as measured in F08. The overlay's very small WiFi RX buffer pools were **not** promoted: the image fits DRAM and IRAM with ESP-IDF's default pools (10 static and 32 dynamic RX buffers, 32 dynamic TX buffers, 5 management buffers), and larger pools lose fewer frames under dense traffic. Revisit them only if the physical run shows free heap pressure or if `wifi` drops appear that the rings do not explain. The F08 overlay files stay in the tree because the historical records reproduce with them.

**Known limits until the board runs it**

- Whether `esp_wifi_set_channel` followed by `esp_wifi_get_channel` agrees with the request while promiscuous mode is on is unverified. A refusal or a different read-back channel surfaces as a `set channel` fault, not an abort.
- A dwell whose clock stops advancing (many wakes without `NowUs` moving) makes `Step` return without stopping or reporting the window; the next `Step` resumes that same window, and the ESP32 driver yields one tick (`Yield`) so the radio task cannot spin. A stalled window never counts toward clearing a fault.
- Tick granularity is 10 ms (`CONFIG_FREERTOS_HZ=100`), so a window's stop can run up to 10 ms past its deadline. The observed time is clipped to the deadline and the late frames are counted as outside-window.
- BLE reports that are still in the HCI buffers when `EndWindow` is called, and frames that arrive while the receiver is being stopped, are counted as outside-window rather than attributed to the window; expect small non-zero counts at every window end.
- A radio whose init failed is not re-initialised; reset the board.
- The WiFi and BLE event rings are drained once per window, so a window with more events than the ring holds (128 WiFi, 96 BLE) drops the oldest and reports the drops.

## Physical check list

For an operator session on the E32R28T. Flash only with the board connected and nothing else holding the serial port. `<port>` is the board's USB serial device; `<build>` is a fresh build directory.

1. **Flash.** `cd firmware && idf.py -B <build> -D SDKCONFIG=<build>/sdkconfig build && idf.py -B <build> -p <port> flash monitor`. Expect `fw.radio: init: wifi=ok (0) ble=ok (0)` within a few seconds and no reset loop. Boot to the monitor screen must not wait for it.
2. **Alternating windows.** Type `DEV:RADIO_STATUS` twice, a few seconds apart. Expect `config generation=1 wifi=on ble=on ... channels=[1,2,...,11]`, a changing `active window` or `last window`, and the `last window` alternating between `radio=wifi` (channels 1..11 in turn) and `radio=ble` with `planned_ms=205`, `observed_ms` ≈ 205 minus the switch cost (about 195-204 ms; a WiFi channel switch is under 1 ms, a BLE scan enable 1.4-5.4 ms, plus up to one 10 ms tick), `end=completed`, and `windows` and `observed_ms` totals growing for both radios.
3. **No HCI trouble.** In the same output `timeouts=0 rejections=0 late=0 unexpected=0 malformed=0 hardware_errors=0 controller_resets=0 vhci_rx_overflow=0`, `credit=1`, both `fault=""`. Leave it running for 10 minutes and repeat; every one stays 0.
4. **Events land in their own windows.** Run with an AP and a BLE advertiser nearby. `events wifi` and `events ble` both grow. `outside_window` and `wrong_radio` stay a small fraction of the events (under about 2%; they are not zero because frames in flight at a window's edges are counted); `wrong_radio` stays at 0. If `wrong_radio` rises, a receiver did not stop.
5. **Status bar.** With the Host linked, the persistent bar shows "WiFi ch1" ... "WiFi ch11" and "BLE scan" in turn, and a problem radio as `gap`, `?`, `off` or `err`. Check the text is legible and does not overflow on the real display.
6. **Toggles reallocate the budget.** `DEV:RADIO_WIFI_OFF`: `DEV:RADIO_STATUS` shows `wifi=off`, a new generation, only `radio=ble` windows after the change, and the bar shows "WiFi off". `DEV:RADIO_WIFI_ON` restores alternation. Repeat for `DEV:RADIO_BLE_OFF` / `DEV:RADIO_BLE_ON` (WiFi alone revisits a channel every ~2.3 s). Then both off: the bar reads "Host only", `DEV:RADIO_STATUS` shows both radios off and no new windows, and the CPU/RAM cards keep updating. Turn them back on.
7. **Stack margin.** `DEV:RADIO_STATUS` (and `DEV:CAPACITY_STATUS`) after 10 minutes of dense traffic: `stack_free_bytes radio` and `hci_worker` stay above about 1 KiB, and `main` and `dev_console` show their usual margin. If the radio task is close to the limit, raise `kRadioTaskStackBytes`; if it has more than 2 KiB spare, trim it.
8. **Touch and the Host link under dense traffic.** Put the board near a busy 2.4 GHz environment (or replay traffic from a second radio). While `DEV:RADIO_STATUS` shows both rings and windows working, tap the settings panel and navigate the screens: each tap responds within about 100-150 ms, and the Host's CPU/RAM cards keep refreshing at 1 Hz with no `Stale`/`Disconnected`. Note `ring_drops`, `message_overflows` and `vhci_rx_overflow`; they should stay 0 or small, and any drops should be reported in the windows (the `drops=` field).
9. **RF hand-off comparison.** Compare the current WiFi stop (promiscuous mode off) with `esp_wifi_stop()`/`esp_wifi_start()` around each BLE window: temporarily change `WifiMonitor::Stop`/`Start`, rebuild, and run item 2 and item 4 for each variant. Record the BLE `observed_ms`, the BLE event rate while a WiFi AP is active, and the hand-off cost. Keep the promiscuous toggle unless the full stop/start measurably increases BLE events or observed time enough to pay for its cost.
10. **No transmission.** With a second radio in monitor mode (a laptop or SDR on the same channels, and a BLE sniffer), watch the board's MAC addresses (`esptool.py read_mac`) through a full 11-channel cycle with both radios on, and with each toggled off and on. Expect no 802.11 frame, probe request or scan request with the board's address, and no BLE scan request (`SCAN_REQ`), at any point including boot. Record the capture file name with the result.
11. **Fault paths.** (Optional, board in hand.) `DEV:RADIO_BLE_OFF`/`ON` several times in a row, then confirm `controller_resets=0` and no `err` on the bar. If any fault appears, record `DEV:RADIO_STATUS` and the `fw.radio` log lines before power-cycling.
12. **Modem sleep is off.** Record `CONFIG_BTDM_CTRL_MODEM_SLEEP` from the generated `<build>/sdkconfig`; it must read `# CONFIG_BTDM_CTRL_MODEM_SLEEP is not set`. With it on (ESP-IDF v5.3.2 ORIG mode) `esp_vhci_host_send_packet` and `esp_bt_controller_disable` can block forever.
13. **Radio task stack on first boot.** Read `stack_free=N` on the `fw.radio: init ...` log line of the first boot. Keep at least 1 KiB spare after trimming `kRadioTaskStackBytes` (8 KiB now).
14. **Beacon channel agrees with the schedule.** In a WiFi window on a channel where an AP is known to beacon, confirm the beacon's DS parameter channel equals the scheduled channel (the read-back check should already have faulted a mismatch).
15. **No cross-radio events after a forced stop failure.** Force a BLE stop failure (for example by timing out the scan disable with a debug build), and confirm `wrong_radio` stays 0 and the BLE fault clears only after the stop works or the controller is cycled.
16. **No transmission, with a second sniffer.** Using a second radio in monitor mode and the board's MAC (`esptool.py read_mac`), confirm there are no ACK, null-data or probe frames from that MAC at any time, including the first 2 s after boot.
17. **BLE advert rate by window.** Compare the BLE advertisement rate seen in BLE windows against the rate during WiFi windows (`wrong_radio` and `outside_window` for BLE). BLE events should come only in BLE windows; record the rates.
18. **Toggles before the Host link.** Run `DEV:RADIO_WIFI_OFF`/`ON` and `DEV:RADIO_BLE_OFF`/`ON` before `CYD:LINK`. DEV commands are not parsed once the link is active.
19. **Command Disallowed on a scan stop.** Record any `scan_stop_already_off` (HCI status 0x0C on a scan disable) in `DEV:RADIO_STATUS`; it is treated as stopped, but a non-zero count means a stop was issued for a scan that was not running. Also record `stale_dropped`.
20. **`esp_bt_controller_mem_release` can abort.** In ESP-IDF v5.3.2 this call runs through `ESP_ERROR_CHECK` inside the library and may abort the board instead of returning an error. If the first boot resets in a loop right after `fw.radio` starts, look for an `ESP_ERROR_CHECK` backtrace there before suspecting anything else.

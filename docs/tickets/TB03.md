## Outcome

Mac RAM counters arrive in complete snapshots and appear in the System card/detail screen with source age and correct missing-data behavior.

## Proposed ownership

Own the macOS RAM collector, RAM scenario fixtures, and `firmware/ui/system/ram/`; consume the System layout/registration interface. TB06 owns battery fields in a separate widget.

## Scope

Collect physical total minus free pages using the sources in [Host metrics](../host-metrics.md); display the agreed headline without relabeling it as application memory or pressure. Integrate one-second collection and simulated error/stale states end to end.

## Resolved promotion questions (from the code)

- **Mach page units.** `host_page_size(mach_host_self())` supplies the page size, and a failure or zero is a failed read (`host/platform-macos/src/ram.rs:98-102`). It is the kernel page size, so 16 KiB on Apple Silicon. `free_count` is info word 0 of `host_statistics64(HOST_VM_INFO64)`, read as `natural_t` pages. The call must return exactly 38 words (`ram.rs:58-60,103-120`). Total is `sysctl hw.memsize` (8 bytes, `ram.rs:80-95`). Used is `total - free_pages * page_size` (`ram.rs:42-46`). Nothing else from the Mach struct is read.
- **Definition against [host-metrics.md:12](../host-metrics.md).** "Physical total minus free pages; includes reclaimable caches; `hw.memsize` and Mach `HOST_VM_INFO64`" matches the code, and the module header says so (`ram.rs:3-6`). The code never relabels it as application memory or pressure. Because inactive, file-backed and purgeable pages are not in `free_count`, the figure is Activity Monitor's "Memory Used" plus roughly "Cached Files". It is expected to read higher than "Memory Used" (see the physical check list). Mach `free_count` includes speculative pages that `vm_stat` prints separately, so `vm_stat` "Pages free" plus "Pages speculative" equals it.
- **Bounds.** Group key 5 has five required fields (availability 0-4, used u64, total u64, source age u32 ms, freshness 0/1). Used is at most total, and unknown extra keys are skipped ([CORE_PROTOCOL.md:52](../../protocol/CORE_PROTOCOL.md); C++ `ReadRamGroup`, `protocol/core/cpp/protocol.cpp:516-550`; Rust `decode_ram_group`, `host/protocol/src/lib.rs:811-840`). Both encoders refuse used above total (`protocol.cpp:248`). The Host collector additionally maps a failed read, zero total, or free above total to availability `Error` with no value (`ram.rs:41-48`), and `hostcore/src/groups/ram.rs:14-20` then sends used 0, total 0, age 0, `Fresh`. The Host always sends source age 0 and freshness fresh, because the read is instant. The device derives staleness itself.
- **Fixtures.** `protocol/fixtures/ram-snapshot-v1*.hex` (golden 8 of 16 GiB at 250 ms, max-u64, used-exceeds-total, missing-field, duplicate-key, duplicate-group, not-a-map, unknown-field, unknown-nested, unknown-too-deep, bad-availability, bad-freshness, age-overflow, noncanonical) plus `storage-snapshot-v1-with-ram.hex` and `-with-bad-ram.hex`. They are built by `protocol/tools/gen_vectors.py:157-200` and listed as `ram-*` rows in `protocol/fixtures/parity-matrix.txt:57-70,94-95`. Host collector fixtures are the injectable `MemorySource` closures in `ram.rs:131-170` and `ScriptedCollector` in `host/metrics/src/lib.rs:305-335`. `RamReading` is `host/metrics/src/lib.rs:85`.
- **Firmware and slot.** `RamMetricState` is `firmware/domain/include/firmware/domain/host_state.hpp:28-37`. It is applied at `firmware/domain/src/host_state.cpp:52-60` and goes stale 3 s after receipt (`host_state.cpp:128-129`). The card is `MakeRamCard` (`firmware/domain/src/cards/ram_card.cpp:16-36`): `--` with no arc before data; `--` plus `Unavailable`/`Read error`/etc. when not Available (`card_registry.cpp:52-65`); otherwise a percentage dial with `used / total GB` (binary GiB, one decimal) under it. Retained or link-lost data is dimmed and prefixed `Last `. The card is registered second (`card_registry.def:9`) and is the middle of the three 101x96 px dials, CPU, **RAM**, Storage, on the dark Overview ([ui-design.md:30](../ui-design.md)). The Host console line prints `ram N / M GB` or `ram unavailable` (`hostcore/src/groups/mod.rs:110-118`).
- **Allocation by C02.** RAM is a registry card and needs no layout change. Both the simulator's `system-screen` scenario and the metric-cards scenario check this.

## Acceptance scenarios

1. **Collector arithmetic.** Used is total minus free (`ram::tests::used_is_total_minus_free`); a failed read, zero total, or free above total is `Error` with no value, never zero used (`ram::tests::a_failed_or_inconsistent_read_is_an_error_never_zero_used`); the real macOS source gives total of at least 1 GiB, free at most total, and a total that is a multiple of 4096 (`ram::tests::the_real_source_reports_plausible_memory`).
2. **Wire contract.** Both codecs round-trip the golden group and reproduce its bytes, and the encoder refuses used above total (`tests::ram_group_round_trips_and_decodes_to_the_golden_values`). Every `ram-*` row of `parity-matrix.txt` agrees between C++ and Rust (`parity: ... 0 mismatch(es)`).
3. **Host to display state.** A RAM group reaches the firmware state, and a later snapshot without the group keeps the last reading while CPU updates (`a_ram_group_reaches_the_firmware_state_and_may_stop_being_sent`). The daemon reports the `ram` group in `status` once paired (`status_reports_every_link_state_from_no_device_to_paired`, `host/hostcore/tests/daemon.rs:333-372`).
4. **Card behaviour (simulator `metric-cards`, `simulator/src/scenarios/metric_cards_scenario.cpp:89-101`, transcript `simulator/scenarios/metric-cards.expected`).** No data shows `--`; 8 of 16 GiB shows `50%` / `8.0 / 16.0 GB`; temporarily unavailable shows `--` / `Unavailable` with a zero bar while CPU stays live; recovery shows 75%; 2.9 s after the group it is still fresh; 3.1 s shows `Last 75%`, dimmed, while CPU is still live; 15.1 s without a frame keeps both retained and dimmed.
5. **Overview slot (simulator `system-screen`, `simulator/src/scenarios/system_screen_scenario.cpp:228-262`).** RAM is the second card and a dial; before data it shows `--` with a hidden arc; live it shows `50%`, `8.0 / 16.0 GB` and an arc of 500; a read error shows `--` / `Read error` with a hidden arc while CPU is unaffected; it recovers; and when stale it reads `Last 50%`, dimmed, with the dial decayed to neutral. The scenario also checks that every part fits 320x240 without overlap.
6. **CPU and pairing intact.** The CPU assertions in 4 and 5 and the pairing tests in `host/transport/tests/link_parity.rs` pass in the same runs.

## Physical check list

For an operator session on the board with the Host paired. Record the commit flashed, the port, the Mac model and RAM size, and the date. Also record the claimant and the release of the board in the coordinator's log.

1. **Display smoke.** Flash and pair (`./dev run host ...` as in TB02). The Overview shows the RAM dial as the middle of the three dials, titled RAM, with an arc, a percentage in the centre, and `used / total GB` under it. Record whether the text is legible and fits the 101 px dial for a typical value (for example `73%`, `11.7 / 16.0 GB`) and for a long one (for example `128.0 / 128.0 GB`, `100%`). Photograph or note the result.
2. **Reading versus Activity Monitor.** Within a few seconds of each other, note the board's RAM percentage and `used / total GB`, the Host console line (`ram N / M GB`), and Activity Monitor's Memory tab: "Physical Memory", "Memory Used" and "Cached Files". Also run `sysctl hw.memsize` and `vm_stat`. Expected: total equals "Physical Memory" (GiB-based) and `hw.memsize`; the board's used is above "Memory Used" by about "Cached Files" (the documented definition includes reclaimable caches), and equals total minus (`Pages free` + `Pages speculative`) x page size from `vm_stat`, within a few hundred MB of churn. Record all numbers; do not accept "equals Memory Used" as the pass criterion.
3. **Tracks load.** Start a memory-heavy task (for example a large file copy, then a process that allocates several GB). The dial and percentage move within about two seconds, and the percentage never reads 0% while the Mac is running.
4. **Stale and offline behaviour.** With RAM showing a value, stop the Host (`./dev run host -- stop` or the equivalent daemon stop, or unplug USB). After about 3 s the RAM dial dims, reads `Last NN%`, and keeps its `used / total GB`; after 15 s the status bar says `Disconnected` and the retained RAM value is still shown, never `0%` or blank. Restart the Host: the dial returns to live without a reboot. Record the times observed.
5. **Missing data.** If a RAM read error can be provoked, or with a debug Host build that sends an `Error` group, the dial shows `--` and `Read error` with no arc and CPU stays live. Otherwise mark as simulator-only.
6. **Resource overhead.** Record Host CPU use of the daemon before and after enabling the RAM group (`ps -o %cpu,rss -p <hostd pid>` over 60 s, expected a small fraction of a core) and the board's `DEV:CAPACITY_STATUS` (heap, LVGL pool, task stack headroom) with and without RAM data. The Overview pool use is documented as about 43 KB steady of 57 KB (ui-design.md). Flag any increase attributable to RAM.

## Open discrepancies

Code disagreements found while promoting. No code was changed.

1. **"Retains its age" is not shown.** The outline says the last sample retains its age, and [ui-design.md "Stale host state"](../ui-design.md) says stale cards show data age. `MakeRamCard` (`ram_card.cpp:24-34`) shows only the `Last ` prefix and dimming; no age text appears, and `now_ms` is unused. The retained time is available only through the Host-last-seen/status bar. Decide whether the age is owed on the card or only by the `Last` label.
2. **The wire does not require zero values when RAM is not Available.** TB04's Storage group does require them ([CORE_PROTOCOL.md](../../protocol/CORE_PROTOCOL.md) key 6). Key 5 neither requires nor checks it (`protocol.cpp:538-541`). The Host sends 0/0 (`groups/ram.rs:16-17`), so behaviour is correct today. The card also treats Available with total 0 as `--` with an empty note (`ram_card.cpp:20-23`), which is not misleading but gives no cause text.
3. **No firmware unit test for the RAM card or reducer.** `firmware/domain/tests/test_host_state.cpp` has no RAM case, and there is no card test beyond the simulator scenarios and the C++/Rust link test. The behaviour is covered, but only by the two simulator scenarios.
4. **Schema metadata is stale.** `protocol/schema/core.toml:9` says `max_frame_bytes = 1024` against 2,048 in `protocol/CORE_PROTOCOL.md` and `protocol.hpp:16`. The schema and `protocol/generated/` carry CPU only, and the RAM types are hand-written in both codecs (`protocol.hpp:60`, `host/protocol/src/lib.rs:58`), so the outline's "protocol/schema, protocol/generated" bounds are not there. The bounds live in the codecs and CORE_PROTOCOL.md.
5. **Unit labelling.** Both the card and the Host console print binary GiB as `GB` (`ram_card.cpp:9,31`; `groups/mod.rs:112-116`), which matches Activity Monitor's convention. Storage uses decimal GB (as Finder). The two cards therefore use different GB units side by side.

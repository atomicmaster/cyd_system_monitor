# F06 — Calibrate touch and recover persisted calibration

- **Kind:** Hardware tracer bullet
- **Detail:** Executable
- **Status:** Done
- **Milestones:** M1
- **Depends on:** [F05](F05.md)
- **Board:** Exclusive E32R28T session

Read [dispatch and completion rules](README.md#dispatch-and-completion) before starting. Command names below are planned deliverables, not tools that already exist.

## Outcome

A first boot guides five-point calibration; later boots reuse validated calibration, and an unusable calibration can be cleared locally or over a development USB recovery path.

## Ownership and inputs

Own `firmware/platform/esp32/touch/`, calibration NVS records, `firmware/domain/calibration/`, and `firmware/ui/calibration/`. Coordinate the diagnostic entrypoint with F05's owner. Consume the [profile requirements](../../hardware/profiles/lcdwiki-esp32-32e-2.8/README.md).

## Work

1. Implement XPT2046 input with a provisional SPI arrangement suitable for touch; record it for F08 to validate under combined load.
2. Implement five guided targets and separate validation targets, explicit error limits, landscape mapping, and checksummed profile/orientation/schema identity.
3. Add recalibration entry from diagnostics and a bounded development USB clear-calibration command. Mark its framing as development-only; TB02 replaces it with the negotiated product command.

## Acceptance

- Physical taps validate independently of calibration targets; invalid transforms are rejected.
- Compatible records survive power cycles; torn, incompatible, or corrupt records return to calibration rather than accepting bad coordinates.
- The USB recovery path works when touch navigation is unusable; board operation remains recoverable through BOOT/RESET.
- Recorded limits and tests cover coordinate corners, transforms, and validation failures without claiming RF/load performance yet.

## Verification and handoff

Run `./dev check firmware`, `./dev run simulator -- calibration`, and `./dev run hardware -- calibration --port "$CYD_PORT"`. Document operator taps and power-cycle evidence. Hand off calibration record ownership and the provisional SPI arrangement to F08/C01.

## Evidence

Base commit `b2e2e4e`. No physical board is available here (see F05's Evidence section for the shared environment constraints). This ticket is **not** marked Done: real touch taps, real persistence across a physical power cycle, and a real USB-recovery session are unproduced.

**Implemented and integrated:**
- `firmware/tools/generate_profile_header.py` extended to emit touch SPI pins (`kTouchSclk/Mosi/Miso/Cs/Irq`) and calibration parameters (`kTouchCalibrationTargets`, `kTouchCalibrateOnFirstStart`).
- `firmware/domain/calibration/` (new module, own `CMakeLists.txt` fragment wired into `firmware/domain/CMakeLists.txt` via `include()`): `RawTouchSample`, `ScreenPoint`, the 5 ordered `kCalibrationTargets` (documented order: top-left, top-right, bottom-right, bottom-left, center), `AffineTransform`, `ComputeAffineTransform` (least-squares 3x3 normal-equations solve per axis, returns `std::nullopt` on a near-singular/degenerate fit), `ApplyTransform`, `ValidateTap` (Euclidean-distance acceptance against a documented provisional 15px default), and `CalibrationRecord`/`ComputeChecksum` (hand-rolled CRC32)/`IsRecordValid`, which checksums the transform together with profile id/orientation/schema version identity per the profile README's requirement.
- `firmware/platform/esp32/touch/`: XPT2046 driver implemented as bit-banged/software GPIO SPI (no hardware SPI peripheral), sending the standard 0x90/0xD0 command bytes with 4-sample averaging, explicitly commented `// PROVISIONAL` citing the profile README's open three-buses-vs-two-controllers question.
- `firmware/platform/esp32/nvs/calibration_store.{hpp,cpp}`: `LoadCalibrationRecord`/`SaveCalibrationRecord`/`ClearCalibrationRecord` over the `nvs_flash`/`nvs` C API, storing a fixed-layout blob; load treats a missing key, a wrong blob size, or an `IsRecordValid` failure identically as "not calibrated" rather than crashing.
- `firmware/platform/esp32/dev_console/`: a bounded, explicitly-labeled development-only UART line-command listener (`DEV:CLEAR_CALIBRATION`) calling `ClearCalibrationRecord()`, commented as a placeholder TB02 replaces.
- `firmware/ui/calibration/`: `CalibrationFlow` state machine (`kGuiding` -> `kValidating` -> `kAccepted`/`kRejected`), driven by `SubmitRawSample()` so the simulator (or real touch) can inject taps one at a time; a separate `kValidationTargets` array (4 edge-midpoints) distinct from the 5 calibration targets, satisfying "physical taps validate independently of calibration targets."
- `firmware/domain/tests/test_calibration.cpp`: exact transform recovery from noiseless synthetic points, two degenerate-input rejection cases (collinear, coincident), validation accept/reject at the exact error boundary, all-four-corner landscape mapping, checksum round-trip, and three corruption-detection cases (transform bit-flip, profile_id change, schema_version change) plus an incompatible-orientation rejection case.
- `firmware/main/main.cpp` now wires all of the above into the actual boot path (an earlier draft of this diff left it unwired -- caught and fixed during review before this evidence was recorded): on boot it loads the stored record via `LoadCalibrationRecord` and skips straight to the diagnostic screen if it validates; otherwise it constructs `CalibrationFlow` and polls `Xpt2046Touch::ReadRaw()` once per loop iteration with edge-triggered touch-down detection (so one physical tap advances the flow exactly once, not once per poll while held), calling `SaveCalibrationRecord` and switching to the diagnostic screen once `kAccepted`, and `Reset()` on the next tap after `kRejected`. `BuildDiagnosticScreen` now returns a real `recalibrate_button` handle (only offered when touch is present) that `main.cpp` wires to tear down the diagnostic screen and re-enter `CalibrationFlow`, closing F06 Work item 3 ("Add recalibration entry from diagnostics").

**First physical flash session (operator-reported, 2026-09-16):** four bugs surfaced and were fixed and reverified in this session -- see F05's Evidence for the full account (dev-console UART crash, LVGL tick never advanced, an async-flush race corrupting the draw buffer, missing RGB565 byte swap, and a wrong MADCTL mirror combination). All four were exercised through F06's own calibration screen, since the board has no stored calibration record and boots straight into `CalibrationFlow`. The operator confirmed, after the final fix, that the guided calibration screen ("Calibrate target 1 of 5") renders crisp, color-correct, and correctly oriented. This directly satisfies the display-quality precondition for the rest of F06's checklist -- it does not yet satisfy the checklist itself, since no physical tap has been performed against it. The `mirror(true, true)` finding also seeded [docs/roadmap.md](../roadmap.md)'s new V1 Settings-configurable landscape flip, since `mirror(false, false)` is this orientation's non-mirrored 180-degree counterpart and the calibration record's existing `orientation` identity field is exactly the mechanism that future setting will use to force recalibration on a flip.

**Second physical session: full calibration completed (operator-reported, 2026-09-16):** the operator added a visible tappable target marker (see F05's Evidence -- `firmware/ui/calibration/calibration_flow.{hpp,cpp}` gained `target_marker_`, a positioned/colored circular `lv_obj`, since the calibration screen previously showed only status text with nothing to actually tap) and worked through three more real bugs with UART diagnostic logging added specifically for this session (`PumpTouchDiagnostics()` in `main.cpp`, `Xpt2046Touch::IrqAsserted()`/`ReadRawIgnoringIrq()` in `touch.{hpp,cpp}`, all still present in the tree as documented DIAGNOSTIC helpers, not removed):
- A "no response" first attempt turned out to be the main loop stalling indefinitely: `lv_timer_handler()` returns `LV_NO_TIMER_READY` (`0xFFFFFFFF`) once idle, and `vTaskDelay(pdMS_TO_TICKS(sleep_ms))` was never clamping that, turning a normal idle report into an effectively infinite sleep the moment the first screen finished rendering -- silently starving touch polling and all further logging, with no crash and no watchdog trip (the loop was genuinely blocked in a legitimate wait, not spinning). Fixed by clamping the loop's sleep to a small bound (20ms) regardless of what LVGL reports.
- Once unblocked, the bit-banged XPT2046 driver worked correctly on the first real attempt: `touch-down` log lines showed `IrqAsserted()` firing and plausible, monotonically-varying raw X/Y values for a full guided calibration (5 targets, `stage=0`) followed by validation (4 targets, `stage=1`), ending in `PersistAndShowDiagnostic()`. The `kBitBangDelayUs=2`/command-byte choices needed no changes.
- The validation-accepted transition (`SubmitRawSample` -> `PersistAndShowDiagnostic` -> `NVS save` -> `ShowDiagnosticScreen`) triggered a real stack overflow (`vApplicationStackOverflowHook`) on the `main` task. This was the first time real hardware had ever reached `BuildDiagnosticScreen()` (every earlier session got stuck in calibration or crashed first), and it reproduced deterministically on the next cold boot too, which loads the now-valid saved record and goes straight to the diagnostic screen -- confirming the fault is in building/rendering that screen, not in calibration submission itself. Root cause: ESP-IDF's default main-task stack (3584 bytes) is too small for LVGL rendering plus this firmware's own screen-building code, all running directly on `app_main`'s task rather than a dedicated task. Fixed via `CONFIG_ESP_MAIN_TASK_STACK_SIZE=16384` in `firmware/sdkconfig.defaults`; reverified with a clean 15-second post-flash boot capture showing the diagnostic screen loads (`have_valid_calibration=1`) and stays up with no crash.

This fully satisfies F06's core functional loop: guided calibration -> validation -> persistence -> reload on next boot -> diagnostic screen, all confirmed on the physical board.

**Third session: recalibrate button and layout (operator-reported, 2026-09-16):** the diagnostic screen's `recalibrate_button` never responded to taps. Root cause, found via targeted diagnostic logging (an `indev press:` log inside the LVGL pointer-indev read callback, and a `recalibrate_button bounds:` log of its actual on-screen rect): `lv_indev_create()` binds the new input device to `lv_display_get_default()` **at the moment it is called** -- `main.cpp` called it before `board::InitBoard()`, which is where the real `lv_display_t` is created (deep inside `display::InitDisplay()`), permanently binding the indev to no display at all. LVGL logs a warning for exactly this case ("no display was created so far"), but `LV_USE_LOG 0` in `firmware/ui/lv_conf.h` silently swallows all LVGL logging, which is why this went unnoticed until physical testing. Confirmed via the diagnostic logs: `PumpTouchDiagnostics()`'s independent poll caught `irq_asserted=1` for real taps, but the indev's own read callback never logged a press at all despite running roughly 30x more often -- proving the SPI/IRQ path was fine and the indev callback specifically was never functioning. Fixed by moving `lv_indev_create()`/`lv_indev_set_type()`/`lv_indev_set_read_cb()` to after `InitBoard()` succeeds. Operator confirmed the recalibrate button now works.

Also in this session: `firmware/ui/calibration/calibration_flow.cpp` gained a separate static title label ("Touch Screen Calibration", top-half center) distinct from the dynamic progress label (bottom-half center, was previously the only text and sat close enough to the bottom-mid validation target to risk visual overlap) -- operator confirmed both are now clear of every target marker.

**Fifth session: DEV:CLEAR_CALIBRATION over the real serial connection (2026-09-16):** with a valid calibration record already saved from the earlier session, sent the literal ASCII line `DEV:CLEAR_CALIBRATION\n` directly over `/dev/cu.usbserial-140` (via a small pyserial script, not `idf.py monitor`, since the goal was just to write one line and capture the response). UART logged `fw.dev_console: received DEV:CLEAR_CALIBRATION: clearing calibration record` immediately. Reset the board (RTS-line toggle, equivalent to a normal reset) and captured the resulting boot log: `fw.main: boot: entering guided calibration (no valid stored record)` -- confirming the record was genuinely erased in NVS, not just logged, since a stale/corrupt/missing record is exactly what routes boot back into `CalibrationFlow` per `main.cpp`'s `have_valid_calibration` check. Full round trip confirmed: command received -> record cleared -> next boot re-enters guided calibration.

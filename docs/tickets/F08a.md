# F08a — Bound and measure the operational UI capacity slice

- **Kind:** Feasibility subtask
- **Detail:** Executable
- **Status:** Awaiting hardware — instrumentation, bounded capacity-slice UI,
  and simulator coverage are integrated (Work items 1-4, 6); the physical
  board session (Work item 5) and its measured peak/low-water evidence are
  still missing. See the [feasibility
  record](../../hardware/profiles/lcdwiki-esp32-32e-2.8/development/feasibility.md#f08a-ui-capacity-slice-build-time-result-no-physical-board).
- **Milestones:** M1a
- **Parent:** [F08](F08.md)
- **Depends on:** [F06](F06.md), [F07](F07.md)
- **Board:** Shared E32R28T session; serialize flashing with F08

Read [dispatch and completion rules](README.md#dispatch-and-completion) before
starting. This subtask supplies a UI/runtime budget to F08; it does not close
F08 or M1a without F08's subsequent combined radio evidence.

## Outcome

A bounded, representative operational UI slice has measured memory and
responsiveness evidence on the E32R28T. The result distinguishes the current
diagnostic UI's lower bound from the MVP's realistic worst normal UI state, so
the F08 capacity decision is based on a defensible budget rather than an
assumed screen cost.

## Ownership and inputs

Own firmware UI capacity instrumentation, the representative capacity slice,
its simulator fixtures, and its physical measurement record. Reuse F06's
calibration flow and F07's diagnostic/profile adapters; do not redesign their
accepted behavior. Consume F08's feasibility record and the product's MVP UI
requirements. Keep product radio policy and final combined-load proof in F08.

## Work

1. Add instrumentation that records LVGL pool peak/available capacity, minimum
   heap, and FreeRTOS task-stack low-water marks for the main, display-related,
   console, and any new UI tasks. Make the readings visible through the
   diagnostic UI or UART, with units and build identity.
2. Implement one bounded operational capacity slice rather than the complete
   product UI: live monitor/status, a maximum-size Alert list, Alert detail or
   overlay, and Settings navigation. Use the actual MVP visual components
   where known; placeholders are permitted only when their object count, text
   length, refresh behavior, and memory reservation are explicit.
3. Declare and enforce upper bounds for visible rows, each label/string,
   transient detail content, screen/overlay count, and refresh cadence. Do not
   load unbounded history into LVGL or create a full-frame buffer.
4. Add simulator coverage for the maximum object tree and maximum strings,
   including navigation that creates and destroys the capacity-slice screens.
   Verify that the bounded UI remains valid after repeated navigation.
5. On the board, exercise calibration, diagnostic, and the capacity slice with
   active touch, display refresh, representative one-second serial traffic,
   and normal flash activity. Record peak values and visible responsiveness.
   If the selected radio approach is buildable, repeat under F08's scheduled
   radio load; otherwise label this result as UI-only evidence.
6. Derive a conservative UI/runtime DRAM budget, identify reclaimable versus
   non-reclaimable allocations, and hand the values and measurement limits to
   F08's radio-capacity decision.

## Acceptance

- The capacity slice represents bounded normal MVP operation, not only the
  calibration/diagnostic lower bound; its maximum object and string counts are
  documented and testable.
- LVGL pool peak, minimum free heap, and task-stack low-water marks are
  measured on named hardware with the flashed commit and exact build config.
- No screen requires a full-frame buffer; visible rows, refresh cadence, and
  transient content remain bounded during repeated navigation.
- Simulator fixtures cover the declared maximum UI state, while physical
  evidence records touch/display behavior and the measurement method.
- The resulting RAM budget explicitly says whether the UI can safely release
  capacity for radio. It does not claim a combined radio/UI pass unless F08's
  radio run was performed.

## Verification and handoff

Run `./dev check all` and the capacity-slice simulator scenario. During the
board session, record the port, operator actions, flashed commit, sdkconfig,
measurement logs, peak/low-water values, and screen-bound table in F08's
feasibility record or a linked profile evidence file. Hand F08 a conservative
UI/runtime budget and the exact remaining headroom; keep F08 blocked when the
radio approach or physical combined run is still missing.

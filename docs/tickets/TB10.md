## Promotion decisions and metadata

TB10 owns `firmware/platform/esp32/radio/wifi_monitor.*`, `firmware/domain/include/firmware/domain/wifi_observation.hpp`, `firmware/domain/src/wifi_observation.cpp`, the shared handoff below, `firmware/ui/include/firmware/ui/wifi_screen.hpp`, `firmware/ui/src/wifi_screen.cpp`, `simulator/fixtures/wifi_observation.hpp`, `simulator/scenarios/wifi_observation.cpp` and `simulator/scenarios/wifi-observation.expected`. The integration owner serializes shared build, navigation and command registration. TB09 retains scheduler ownership: its candidate world-safe default is channels 1–11, subject to pinned-driver validation (ADR 0026).

Capture management, control and data metadata: change the management-only callback guard and configure `WIFI_PROMIS_FILTER_MASK_MGMT | WIFI_PROMIS_FILTER_MASK_CTRL | WIFI_PROMIS_FILTER_MASK_DATA`, plus an explicit control-subtype filter covering supported control subtypes. Never enable `WIFI_PROMIS_FILTER_MASK_FCSFAIL`. FCS is driver-validated only when `rx_ctrl.rx_state == 0`; other paths use invalid or unknown, never infer valid from absence of an error. A host test pins both filters and FCS mapping; board captures verify them. If the required capture cannot meet the budgets, **Decision needed (product owner):** approve a scope reduction or fund redesign; recommendation: retain all three types and redesign first.

The fixed event contains protocol, window ID and configuration generation (`u32`), arrival monotonic microseconds (`u64`), channel (`u8`, 1–14), RSSI (`i8` dBm with validity), frame type/subtype (`u8`, 0–2/0–15), receiver, transmitter and BSSID (six bytes each with independent presence bits), 12-bit sequence number (`u16` plus presence), retry (`bool`), FCS (valid/invalid/unknown), and FCS-inclusive on-air length (`u16` bytes). Type, subtype, length and PHY feed activity; roles and sequence feed inspection and TB12; RSSI feeds Signal Strength. Sequence is diagnostic, never deduplicates frames. Deauth subtype 12 and disassoc subtype 10 feed TB12, including protected frames without reading their bodies.

Use type/subtype and DS bits for address roles. ACK/CTS have only a receiver in their short control header: no absent transmitter may become an all-zero identity. Validate complete headers before each read, including fourth address for ToDS+FromDS and QoS control for QoS data. Unsupported control/header forms count only when their required header is complete, with unknown roles absent; malformed, truncated and SDK metadata-only packets are separately counted, never fabricated as complete frames or rule evidence. Treat `sig_len` as FCS-inclusive and validate minimum header plus four FCS bytes before reads; pin this assumption against the SDK and physical captures.

For beacon and probe-response management frames, parse the bounded IE list in the callback: extract SSID length 0–32 and bytes with presence and hidden flags; zero-length or all-zero SSID is hidden, missing IE is absent, malformed IE rejects the label and increments malformed count. Copy this bounded label across the callback boundary; never retain other frame body or payload. Labels live only in the 64-entry BSS RAM table, expire 5 minutes after last sighting or on eviction, reboot or configuration change; no durable SSID history. ADR 0007 permits raw addresses locally. Escape labels at render time into a 129-byte buffer (at most four output bytes per input byte plus terminator); never use labels as identity. TB18 and the product owner own export and retention policy.

Extract SDK PHY rate, MCS, bandwidth, guard interval and aggregation indicators with validity bits. Estimate received airtime from FCS-inclusive length and the supported PHY's nominal bitrate plus documented preamble/header and symbol rounding; for aggregation, count only known per-MPDU transmission duration and do not invent shared overhead. Sum bounded integer microseconds with saturation. Unsupported or missing PHY metadata contributes to an unknown count, not zero airtime. Label every result **estimated** and disclose excluded unknowns; it is sampled received airtime, not channel congestion. Pin formulas and vectors to the SDK/PHY definitions during implementation.

## Shared radio handoff contract (TB10 owner)

TB10 owns `firmware/domain/include/firmware/domain/observation_event.hpp`, new `firmware/domain/include/firmware/domain/observation_handoff.hpp` and `firmware/domain/src/observation_handoff.cpp`, and coordinated edits to `firmware/domain/include/firmware/domain/radio_runner.hpp`, `firmware/domain/src/radio_runner.cpp`, `firmware/platform/esp32/radio/observation_gate.*` and `radio_driver.*`. TB11 owns BLE extraction and calls this seam; integration owner serializes shared edits. The API, in `firmware::domain`, is:

```cpp
class ObservationHandoff {
 public:
  bool Stage(const ObservationEvent& event); // radio task, capture order
  void MarkLoss(uint32_t window_id, uint32_t generation, LossKind kind);
  void Finalize(const WindowReport& report, ObservationConsumer& consumer);
  void ConfigurationChanged(uint32_t generation, ObservationConsumer& consumer);
  void Fault(Radio radio, ObservationConsumer& consumer);
};
class ObservationConsumer {
 public:
  virtual void OnAccepted(const ObservationEvent&, uint64_t sequence) = 0;
  virtual void OnWindow(const WindowReport&, bool loss_uncertain) = 0;
  virtual void OnConfiguration(uint32_t generation) = 0;
  virtual void OnFault(Radio radio) = 0;
};
```

Define `LossKind` as ring, staging, VHCI packet, late processing or report loss; fixed records carry window ID and generation. `Stage` copies into a fixed 64-event staging array, never allocates; false marks that window lossy. `DrainEvents` on the radio task stages in ring order after gate closure and before report finalization. `Finalize` matches both ID and generation, and emits eligible events in capture order before the matching report. Eligibility requires observing state and `observed_ms * 2 >= planned_ms`; gap, missing report, wrong generation or fault discards staged evidence. A single radio-task-owned `uint64_t` per-boot acceptance counter starts at 1 and is assigned exactly once immediately before `OnAccepted`; no other producer assigns it. Overflow of that counter faults the handoff rather than wrapping. Consumers combine it with boot identity; TB12/14/15 use report observed time, not ledger totals. Events in eligible lossy windows remain lower-bound evidence, never observed quiet.

`Finalize` completes the old generation before `ConfigurationChanged` is delivered and before any new-generation event; a fault invalidates unfinished windows and is delivered before later events. Missing or lost reports discard their staged events and signal uncertainty; never invent a report or quiet. Stage overflow and ring eviction mark the affected window lossy. The HCI transport records a monotonic loss marker when its advertising packet buffer overflows; associate it with an open BLE window, or conservatively mark any possibly overlapping pending BLE window uncertain. A packet may contain several reports: packet loss is not an exact report count. Track HCI packets by arrival timestamp and worker completion watermark; a packet arriving before deadline but processed after gate closure marks its original window uncertain, even if it cannot be recovered. Finalize only after a bounded worker barrier; timeout marks uncertainty, never waits indefinitely. If attribution or the report queue fails, mark all potentially affected pending windows uncertain and prohibit quiet. Propagate uncertainty with the report to rule consumers; it is equivalent to nonzero drops for recovery, not a fabricated exact count. No report or uncertain time advances recovery. Ordering, late packets and overflow are tested under generation changes.

## Combined memory and CPU worksheet

Use separate fixed protocol ring element types, not the current event containing both structs. Four 128-bit UUID slots alone require at least 68 B per BLE event. Enforce `static_assert` size ceilings and measure the linked and heap allocations; each 16 B added to the current shared event would cost 3,584 B across 224 ring slots. Budget **total allocations**, not incremental claims:

| Allocation | Ceiling |
| --- | ---: |
| WiFi ring: 128 × 112 B | 14,336 B |
| BLE ring: 96 × 128 B | 12,288 B |
| staging: 64 × 128 B | 8,192 B |
| WiFi 64 BSS (including labels) + 64 transmitter entries | 6,144 B |
| BLE 128 transmitter entries | 4,096 B |
| Two bounded snapshot copies, both radios | 4,096 B |
| Locks, loss markers and queue bookkeeping | 1,024 B |
| Additional LVGL objects and bounded render buffers | 4,096 B |
| **Combined ceiling** | **54,272 B** |

These ceilings include alignment and must be checked against actual sizes, including the existing allocations they replace; do not add the full total to the old ring allocation. TB09's 70,092 B static DRAM and 18,046 B IRAM remaining are link-map figures, not available heap; LVGL, stacks and radio buffers also use heap. No additional IRAM is budgeted. Require at least 20 KiB minimum free internal heap and 1 KiB stack margin on each radio/HCI task in the combined physical run; otherwise reduce allocation or redesign. Reserve TB15's separate 4.2 KiB candidate state before integration.

At 64/64 WiFi and 128 BLE table occupancy, measure callback extraction at 500 WiFi frames/s (including 100 maximum-length SSID-bearing frames/s), HCI-worker extraction at 500 BLE reports/s in multi-report packets, and radio-task aggregation at a full ring per 205 ms window. Each stage has a **5 ms maximum per 205 ms window** acceptance ceiling, measured separately including worst callback/worker batch; this is a ceiling to prove, not measured feasibility. Track lost frames/reports; any loss marks the window lower-bound and blocks quiet.
